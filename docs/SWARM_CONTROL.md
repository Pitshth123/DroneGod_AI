## 2. การเลือกโดรน (Drone Selection)

- **คลิกการ์ดฝั่งซ้าย** = เลือกลำเดียว
- **Ctrl + Click** = เลือกหลายลำ (กดซ้ำเพื่อเอาออก)
- **ปุ่ม FLEET** (ในหมวด FLIGHT) = เปิด → เลือกทุกลำ / ปิด → ล้างการเลือก
- เลือกครบทุกลำเอง → ปุ่ม FLEET ติดอัตโนมัติ; เลือกเองบางลำ → FLEET ดับ
- **ไม่มี checkbox ในแผงขวาแล้ว** — การเลือกทำที่การ์ดฝั่งซ้ายที่เดียว

คำสั่งทุกอย่าง (takeoff / goto / RTL / E-STOP) ยึด "ลำที่เลือก" เป็นเป้าหมาย

## 4. Take off

**2 โหมด** (เลือกที่หมวด FLIGHT):
- **All** — ทุกลำที่เลือกขึ้นพร้อมกัน
- **Sequential** — Head ขึ้นก่อน แล้วลูกขบวนทยอยขึ้น (เว้น ~2.5 วิ/ลำ)

**ความสูง**: ดีฟอลต์ **20 m** ทุกลำ · ตั้งรายลำได้ที่ช่อง `ALT` ใน Bottom Card

**Swarm Take off** = กดปุ่ม `⬆ TAKE OFF` ในหมวด FORMATION/SWARM
→ ระบบ **แนบ Form up ให้อัตโนมัติ** ไม่ต้องกดเอง

## 5. RTL — กลับฐานแบบไม่ชนกัน

### กติกาคำนวณความสูงและจุดลง

ค่า **`RETURN BASE ALTITUDE`** (หน้า SAFETY & SYSTEM) = ชั้นล่างสุดเหนือ home
(ต่ำสุด 15 m) และ **`RETURN MIN GAP`** = ระยะห่างชั้น/จุดลงที่ร้องขอ
โดย core จะ clamp อีกครั้งให้ไม่น้อยกว่า `MinSeparation`

ตัวอย่าง base 15 m, gap 5 m: D1/D2/D3 ใช้ชั้น 15/20/25 m และได้จุดลงคนละจุด
รอบ home ที่ห่างกันอย่างน้อย 5 m

กด **💾 SAVE SYSTEM SETTINGS** เพื่อบันทึกและนำไปใช้ทันที (มี preview สดใต้ slider)

### ลำดับการทำงาน — core คุมทั้ง operation

```
ทุกลำ:      RETURN ไปจุดลงแยก + ชั้นแยก
จากนั้น:    LAND ทีละลำ → ยืนยัน alt<1m และ disarmed → ลำถัดไป
```

ถ้า LAND ลำใดล้มเหลวหรือหมดเวลา core จะหยุดลำดับ ไม่สั่งลำถัดไปลง
และ E-STOP สามารถยกเลิก operation ที่กำลังรันได้

> **ทำไมไม่ใช้คำสั่ง RTL ของ Flight Controller?**
> ArduPilot ใช้พารามิเตอร์ `RTL_ALT` **ค่าเดียวกันทุกลำ** → ทุกลำไต่ไปความสูงเดียวกัน
> แล้วบินกลับจุดเดียวกัน = **ชนกลางอากาศ** จึงให้ core วางแผน RETURN ทั้งชุด
> ตรวจ altitude/radius/geofence ก่อนเริ่ม และแยกจุดลงรายลำ

### สถานะบนการ์ด

ระหว่าง RTL การ์ดโดรนทุกใบ (ซ้ายบน + การ์ดล่าง) จะโชว์ badge `RTL·RETURN`
จน telemetry ยืนยันว่าทุกลำลงพื้นและ disarmed

*(สถานะนี้ต้องโชว์เอง เพราะเราไม่ได้ใช้โหมด RTL ของ FC — FC จึงไม่รายงานว่าเป็น RTL)*

## 6. Collision Detection

ตรวจระยะห่างทุกคู่โดรนแบบ real-time (ทุก 0.7 วิ) ด้วย haversine

| ระยะ | ระดับ | การแจ้งเตือน |
|------|-------|--------------|
| ≤ 3 m | 🔴 critical | banner แดง + toast + log ERROR |
| ≤ 6 m | 🟡 warn | banner เหลือง + log WARNING |

- **แยกชั้นความสูง**: ต่างระดับเกิน 2 m ถือว่าคนละชั้น ไม่นับว่าชน
- ป้ายสถานะบน statusbar: `SEPARATION OK` / `⚠ COLLISION 2` (hover ดูรายคู่)
- บอกชัดว่าลำไหนกับลำไหน: `D3 ↔ D7 ชนกัน/ซ้อนทับ · ห่าง 0.4 m`
- กัน log spam (เตือนซ้ำทุก 8 วิ) แต่ยกระดับเป็น critical เตือนทันที

## 7. Collision Avoidance — ลำดับการเคลื่อนที่

เมื่อสั่งฝูงเคลื่อนที่ ระบบจัดคิว **"ลำที่อยู่ไกลสุดในทิศเดินทางไปก่อน"**

```
5 ลำเรียงหน้ากระดาน   D1 ─ D2 ─ D3 ─ D4 ─ D5   (D1 ซ้ายสุด)
สั่งไปขวา  →  คิว 5 → 4 → 3 → 2 → 1   (Leader ที่ซ้ายสุดขยับท้ายสุด)
สั่งไปซ้าย  →  คิว 1 → 2 → 3 → 4 → 5
```

ใช้กับทั้งปุ่มทิศทาง (D-pad) และการคลิกแผนที่ · ทำงานเมื่อเลือก > 1 ลำ

## 8. คลิกแผนที่ = ทุกลำที่เลือกบินไปพร้อมกัน

คงรูปขบวนเดิม: หาจุดกึ่งกลางกลุ่ม แล้วเลื่อนทุกลำด้วยเวกเตอร์เดียวกันไปเป้าหมาย
→ ระยะห่างระหว่างลำคงเดิมเป๊ะ ไม่บินไปทับจุดเดียวกัน

ถ้า**ไม่ได้เลือกลำไหนเลย** → ไม่บิน + เตือน (กันโดรนสุ่มออกบินเอง)

## 8.1 เป้าหมายกะพริบ + เส้นประนำทาง (Target Indicator & Dashed Path)

เมื่อคลิกสั่งเป้าหมายบนแผนที่:

| องค์ประกอบ | รายละเอียด |
|-----------|-----------|
| **จุดเป้ากะพริบ** | เป้าเล็ง (วงกลม + กากบาท + จุดกลาง) **สีเดียวกับโดรน** กะพริบด้วย CSS `@keyframes tgtPulse` (1.05 วิ/รอบ) |
| **เส้นประนำทาง** | ลากจากตำแหน่งโดรน → เป้าหมาย · สีเดียวกับโดรน · `dashArray: 8 7` |
| **หดสั้นแบบ real-time** | อัปเดตทุกครั้งที่ telemetry เข้ามา (`_updateTargetLine` ใน `updateDrone`) |
| **ล้างอัตโนมัติ** | เข้าใกล้เป้า ≤ 3 m → ลบจุด+เส้นเอง แล้วแจ้ง Python ผ่าน event `target_reached` |
| **เส้นทึบประวัติเส้นทาง** | `trails[]` — **คงไว้เหมือนเดิม ไม่ถูกแตะ** |

โดรนแต่ละลำมีเป้าของตัวเองแยกกัน (สั่งหลายลำพร้อมกันได้ เห็นเส้นประคนละสี)

**API ฝั่ง JS**: `setTarget(id, lat, lon, color)` · `clearTarget(id)` ·
`clearAllTargets()` · `hasTarget(id)` · `targetCount()`

## 8.2 ปุ่ม Cancel Navigation

ปุ่ม **`✖ CANCEL NAV`** ในหมวด FLIGHT (แผงขวา) — กดแล้ว:
1. ตัดลำดับ Waypoint EXECUTE ที่ค้างอยู่ (`_abort_waypoint_execution()`)
2. ล้างจุดเป้า + เส้นประทั้งหมดบนแผนที่ (`clearAllTargets()`)
3. สั่ง `stop_all` → หยุดเคลื่อนที่ทันที
4. สั่ง `hold` → ค้างตำแหน่ง (hover) รอรับคำสั่งใหม่
5. ตัดลำดับ RTL ที่ค้างอยู่ด้วย

สั่งเฉพาะลำที่เลือก · ถ้าไม่มีโดรนเลย ก็แค่ล้างแผนที่ (ไม่ error)

### Hold ทำงานยังไง (สำคัญ — เคยทำให้โดรนตก)

`Hold` **ไม่สลับไปโหมด LOITER** แต่ทำสองขั้น:

1. ถ้ายังไม่อยู่ `GUIDED` → สั่งเข้า `GUIDED` ก่อน (ตัด RTL/AUTO/LOITER ที่ค้างอยู่)
2. ส่ง `SET_POSITION_TARGET_GLOBAL_INT` ไปที่ **พิกัด+ความสูงปัจจุบันของลำนั้นเอง**
   = ตรึงอยู่กับที่จริง ๆ

| กรณี | พฤติกรรม |
|------|----------|
| ยังไม่ armed | ไม่ทำอะไรกับโหมดเลย (คืน ok) |
| ไม่มีพิกัด GPS (`lat==0 && lon==0`) | ส่งความเร็ว 0 แทน กันไหลต่อ + บอกใน audit |
| ปกติ | ตรึงพิกัดปัจจุบันใน GUIDED |

**ทำไมต้อง GUIDED ไม่ใช่ BRAKE** — `BRAKE` ก็ค้างได้เหมือนกันและไม่กินสติ๊กคันเร่ง
แต่คำสั่งอื่นทั้งหมด (Goto / Waypoint / Swarm) ส่ง `SET_POSITION_TARGET` ซึ่ง FC จะเมิน
ถ้าไม่ได้อยู่ `GUIDED` — ถ้าเลือก BRAKE ต้องไปเพิ่มขั้นตอนสลับโหมดกลับให้ทุกคำสั่งถัดไป
ค่าโหมดถูกล็อกไว้ที่ `holdMode` ใน `backend/internal/command/service.go` พร้อมเทสต์กันรีเกรส
(`hold_test.go`)

## 8.3 Tactical Planning — วาดแผนที่ยุทธวิธี

> **แยกจาก Geofence โดยสิ้นเชิง** — geofence = เขตห้ามบิน (บังคับที่ core),
> tactical = วางแผนอย่างเดียว ไม่ส่งไปที่โดรน
> เปิดได้ทีละระบบ (เปิดอันหนึ่งอีกอันปิดอัตโนมัติ) กันคลิกชนกัน

หมวด **TACTICAL PLANNING** ในแผงขวา

| เครื่องมือ | วิธีใช้ |
|-----------|--------|
| **เส้น (Polyline)** | คลิกหลายจุด → ดับเบิลคลิก หรือกด "เสร็จ" |
| **รูปหลายเหลี่ยม (Polygon)** | คลิก ≥3 จุด → ดับเบิลคลิก หรือกด "เสร็จ" |
| **วงกลม** | คลิกจุดศูนย์กลาง → คลิกกำหนดรัศมี |
| **ข้อความ** | ใส่ข้อความในกล่อง → คลิกวางบนแผนที่ |
| **สัญลักษณ์** | อัปโหลดรูป → เลือกจาก dropdown → คลิกวาง |

- **ปุ่มเสริม**: เสร็จ · ย้อนกลับ (undo) · ล้าง (ถามยืนยัน)
- **อัปโหลดสัญลักษณ์**: PNG/JPG/SVG/GIF ≤ 2 MB → ฝังเป็น data URL
  (อยู่ในหน่วยความจำ + ฝังลงไฟล์แผนตอน Save)
- **Save / Load**: ไฟล์ **GeoJSON** (`FeatureCollection`) พร้อม field `icons`
  เก็บรูปสัญลักษณ์ → เปิดที่เครื่องอื่นก็เห็นสัญลักษณ์ครบ

> **ทำไมไม่ใช้ Leaflet.draw / Geoman?**
> โปรเจกต์ออกแบบให้ทำงาน **offline** (tile cache + leaflet ในเครื่อง — `assets/leaflet/`)
> การดึง plugin จาก CDN จะทำให้ใช้งาน offline ไม่ได้ จึงเขียนเครื่องมือวาดเองด้วย
> Leaflet primitives (`L.polyline` / `L.polygon` / `L.circle` / `L.marker` + `divIcon`)
> ซึ่งสอดคล้องกับเครื่องมือ geofence เดิมที่ก็เขียนเองอยู่แล้ว

**API ฝั่ง JS**: `setTacticalTool(tool)` · `setTacticalText(txt)` ·
`addTacticalIcon(name, dataUrl)` · `useTacticalIcon(name)` · `listTacticalIcons()` ·
`finishTactical()` · `undoTactical()` · `clearTactical()` ·
`getTacticalGeoJSON()` · `loadTacticalGeoJSON(js)` · `tacticalCount()`

## 8.5 Waypoint Route Planning — วางแผนเส้นทางบินหลายจุด

| รายการ | รายละเอียด |
|--------|-----------|
| **สวิตช์ Waypoint Mode** | หมวด **WAYPOINT ROUTE** ในแผงขวา — OFF (ดีฟอลต์) = คลิกแผนที่บินทันทีเหมือนเดิม (Direct Flight) / ON = คลิกแผนที่ = วางจุดมาร์คเกอร์แทน ไม่บินทันที |
| **จุดมาร์คเกอร์ + เส้นประ** | วงกลมมีเลขลำดับ สีตรงกับโดรน/Head ที่เลือก + เส้นประ `dashArray:10 6` เชื่อมจุดตามลำดับที่คลิก |
| **โดรนเดี่ยว** | เลือก 1 ลำ → เส้นทางเฉพาะของลำนั้น |
| **Swarm (เลือกหลายลำ/FLEET)** | เส้นทางเดียว = **Leader Path** — ทุกจุดคำนวณด้วยหลักเดียวกับคลิกแผนที่ปกติ (หาจุดกึ่งกลางกลุ่ม เลื่อนทุกลำด้วยเวกเตอร์เดียวกัน) → **รูปขบวน/ระยะห่างคงเดิมทุกจุดตลอดเส้นทาง** สีเส้นทางใช้สีของ Head ถ้าอยู่ในกลุ่มที่เลือก ไม่งั้นสีฟ้ากลาง |
| **UNDO** | ลบจุดสุดท้ายที่วางไว้ (ไม่จำกัดจำนวนครั้ง) |
| **CLEAR ALL** | ลบจุดทั้งหมด (ถามยืนยันก่อน) |
| **EXECUTE ROUTE** | เริ่มบินตามจุดที่วางไว้ทีละจุดจนจบ — ปิดโหมด Waypoint อัตโนมัติกันเผลอเพิ่มจุดระหว่างบิน |
| **รอครบก่อนไปจุดถัดไป (Swarm)** | ทุกลำต้องถึงจุดปัจจุบันก่อน (นับผ่าน event `target_reached` ที่มีอยู่แล้ว) จึงสั่งจุดถัดไป — กันบางลำวิ่งนำหน้าตัดขบวน |
| **ไฮไลต์ / จุดที่ผ่านแล้ว** | จุดที่กำลังบินไปกะพริบ (`.wp-active`) จุดที่ผ่านแล้วสีจาง (`.wp-done`) |
| **Cancel Nav** | ยกเลิกระหว่าง Execute ได้ทันที — ล้างจุดบนแผนที่ + หยุดลอยอยู่กับที่ |
| **แยกจาก Tactical/Geofence** | เปิดได้ทีละระบบ — เลือกเครื่องมือ geofence/tactical จะปิดโหมด Waypoint อัตโนมัติ |

**ทำไมไม่เพิ่ม RPC ใหม่**: reuse `Goto` RPC ที่มีอยู่แล้ว (เหมือนคลิกแผนที่ปกติ) ยิงทีละจุดตามลำดับ
— ไม่ต้องแก้ Go backend / ไม่ต้องเพิ่ม proto message ใหม่

**การตรวจจับ "ถึงจุดแล้ว"**: reuse ระบบเป้าหมาย (`targets{}`/`setTarget`/`_updateTargetLine`)
ที่มีอยู่แล้วจากฟีเจอร์คลิกแผนที่ — จุดมาร์คเกอร์ Waypoint (`waypoints{}`) เป็นภาพเส้นทางที่วางแผนไว้
เท่านั้น ส่วนการนำทาง/ตรวจระยะถึงจุดจริงใช้ระบบเป้าหมายเดิมคู่ขนานกัน (เห็นทั้งเส้นทางเต็ม + จุดที่กำลังมุ่งหน้าไปแบบ real-time)

### 8.5.1 โหมดเส้นทาง: GROUPED vs SEPARATE

| | **GROUPED** (ดีฟอลต์) | **SEPARATE** |
|---|---|---|
| เส้นทาง | เส้นเดียวร่วมกัน | แต่ละลำมีของตัวเอง |
| การวางจุด | คลิก = เข้าเส้นทางร่วม | คลิก = เข้าเส้นทางของ **ลำที่โฟกัสอยู่** (คลิกการ์ดซ้ายเพื่อสลับลำ) |
| การบิน | ทุกลำไปจุดเดียวกันพร้อมกัน **คงรูปขบวน/ระยะห่าง** · รอครบทุกลำก่อนไปจุดถัดไป | แต่ละลำบิน **อิสระ** ตามเส้นทางตัวเอง ไม่ต้องรอกัน |
| Undo/Clear | ทั้งเส้นทางร่วม | Undo = ของลำที่โฟกัส · Clear = ทุกลำ |
| ตรวจกันชน | ไม่ต้อง (ขบวนกระจาย offset ให้อยู่แล้ว) | **ตรวจก่อนบินเสมอ** |
| ใช้ตอน Swarm | ✅ (เส้นทางของ **ลำแม่** — Leader Path) | ❌ ต้องออกจากโหมด Swarm ก่อน |

**ข้อจำกัดโหมด Swarm**: ระหว่าง `swarm.active` จะบังคับเป็น GROUPED เสมอ —
วางเส้นทางได้เฉพาะลำแม่ (Head) และทั้งขบวนบินตาม · ถ้ากด SEPARATE จะถูกปฏิเสธ
พร้อมเด้งปุ่มกลับ · เข้าโหมด Swarm ระหว่างที่ SEPARATE เปิดอยู่ → สลับกลับ GROUPED อัตโนมัติ

### 8.5.2 กันชนก่อนบิน (SEPARATE)

กด Execute แล้ว **ยังไม่สั่งบินทันที** — ตรวจก่อนว่ามีคู่ไหนเสี่ยงชน:

> นับเป็น "เสี่ยง" เมื่อ **จริงพร้อมกันทั้ง 2 ข้อ**
> 1. ต่างระดับความสูง ≤ **2 m** (ถือว่าอยู่ชั้นเดียวกัน)
> 2. เส้นทางเข้าใกล้กัน < **6 m** (รวมกรณีตัดกัน = 0 m)

- คำนวณระยะแบบ **segment-to-segment** ของ polyline ทั้งเส้น (ไม่ใช่แค่จุด)
- รวม "ขาแรก" จากตำแหน่งปัจจุบัน → จุดแรกด้วย
- บินคนละชั้นความสูงชัดเจน → **ไม่นับว่าชน** แม้เส้นทางทับกันบนแผนที่
- เจอ conflict → **บล็อกไม่ให้บิน** + log/banner/dialog บอกคู่ที่เสี่ยงและระยะจริง
  แล้วแนะให้ตั้ง ALT ของแต่ละลำให้ต่างกัน (ช่องในการ์ดโดรนฝั่งซ้าย)

> **ทำไม GROUPED ไม่ต้องตรวจ**: เส้นทางร่วมเส้นเดียว ถ้าเอามาเทียบเป็นคู่จะได้
> ระยะ 0 m ทุกคู่ (เส้นเดียวกัน) = บล็อกผิดทั้งที่ปลอดภัย · ขบวนถูกกระจาย offset
> โดย `group_goto_targets` + มีคิวกันชนตอนส่งคำสั่งอยู่แล้ว

**API เพิ่ม (logic ล้วน)**: `check_route_conflicts()` · `route_min_distance()` · `RouteConflict`

**API ฝั่ง JS**: `setWaypointMode(on)` · `addWaypoint(droneId,lat,lon,color,index)` ·
`removeLastWaypoint(droneId)` · `clearWaypoints(droneId)` · `clearAllWaypoints()` ·
`highlightWaypoint(droneId,index)` · `markWaypointDone(droneId,index)` · `waypointCount(droneId)`

**Logic ล้วน**: `frontend/swarmgod_gui/core/waypoint_logic.py` — `Waypoint`, `WaypointRoute`
(`add`/`remove_last`/`clear`/`is_empty`/`as_pairs`), `waypoint_swarm_targets()`
(reuse `swarm_logic.group_goto_targets`)

### 8.6.1 แจ้งเตือน "เปลี่ยน Head ไม่ได้"

เดิมมีแค่ toast สั้น ๆ ผ่านไปเร็ว ตอนนี้เพิ่ม **banner สีแดง** ค้างด้านบนอธิบายเหตุผลชัดเจน
ทุกครั้งที่ถูกบล็อก (ทั้งจากปุ่มบนการ์ดและ dropdown LEADER) — ระบุว่าไม่ใช่บั๊ก
แต่เป็นการล็อกความปลอดภัยตั้งใจ (`_head_change_block_reason()`):

1. กำลังทำ RTL อยู่
2. มีลำไหนกำลัง TAKEOFF/LANDING อยู่
3. ขบวน Swarm กำลังเคลื่อนที่จริง (มี ground speed)

### 8.6.2 แจ้งเตือนโหมด REMOTE

จุดที่ผู้ใช้งง**บ่อยที่สุด**คือสลับเป็น REMOTE แล้วกดปุ่มอื่นไม่ติดโดยไม่มีอะไรเตือน
ตอนนี้ `_show_banner()` รองรับ `persistent=True` (ไม่หายเอง จนกว่าจะสลับกลับ UI):

- สลับ UI → REMOTE: banner สีเหลือง **ค้างตลอดเวลา** บอกชัดว่าคำสั่งอะไรถูกล็อกทั้งหมด
  (Arm/Takeoff/RC/Waypoint/RTL)
- ทุกครั้งที่กดคำสั่งบินขณะ REMOTE เปิด (`_guard()` บล็อก) → banner เดิม **โผล่ซ้ำอีกครั้ง**
  กันกรณีผู้ใช้พลาดปิดบังเอง
- สลับกลับ UI → banner หายทันที

**Logic**: `app.py` → `_show_banner(text, color, persistent=False)`, `_on_control_changed()`,
`_guard()`, `_on_head_req()`, `_on_leader_combo()`

### 8.6.3 Banner ไม่ทำ layout ขยับ / แผนที่วาบขาว

**ปัญหาเดิม**: `self.banner` เป็น `QLabel` ที่ `setVisible(False)` ตอนไม่มีข้อความ — Qt ไม่เว้น
พื้นที่ให้ widget ที่ `visible=False` ในเลย์เอาต์ ทำให้พอ banner โผล่/หาย ทั้งแถบใต้ topbar
ขยับขึ้นลง 26px และแผนที่ (`QWebEngineView`) วาบขาวชั่วครู่ตอน resize

**แก้**: `self.banner` เป็น **`setVisible(True)` ตลอด** (`_build_ui`) เว้นพื้นที่ 26px ไว้เสมอ
— "ซ่อน" หมายถึงเคลียร์ข้อความ+พื้นหลังโปร่งใส (`_hide_banner()`) ไม่ใช่ `setVisible(False)` อีกต่อไป
`_show_banner()`/`_hide_banner()` แก้แค่ text/stylesheet ไม่แตะ visibility

### 8.6.4 แถบสีสถานะโหมดบน Topbar

โซนระหว่างป้ายโหมด (✈ FLIGHT) กับคำว่า CONTROL เปลี่ยนสีตามโหมดบินปัจจุบันแบบ **จางกว่า
banner** (`border-bottom` alpha 0.35 เทียบกับ banner ที่ทึบ+มีข้อความ) กันไม่ให้สีซ้ำ/แย่งความ
สำคัญกับ banner แจ้งเตือน — ใช้สีชุดเดียวกับ `pill_fmode` (FLIGHT=ฟ้า, SWARM=เหลือง,
RTL=ส้ม, WAYPOINT=เขียว)

**Logic**: `app.py` → `self._mode_strip` (สร้างใน `_build_topbar`, แทนที่ `h.addStretch()`
เดิมด้วย widget ที่ขยายเต็มพื้นที่ว่างแต่มีแค่ border ล่างเป็นสี), อัปเดตสีใน
`_set_flight_mode_badge()`

## 11. บั๊กที่เจอและแก้ (พร้อมต้นตอ)

### 11.1 `SetLeader` ไม่เคยถูก implement ที่ฝั่ง Go
**อาการ**: เปลี่ยน Head ไม่ได้ — กดเป็นลำ 2 แล้วเด้งกลับลำ 1 (ทั้งปุ่มและ dropdown)

**ต้นตอ**: `rpc SetLeader` ประกาศไว้ใน `proto/swarmgod/v1/service.proto` แต่ `api.Server`
ไม่ได้ implement → `UnimplementedSwarmGodServiceServer` กลืนคำสั่ง ตอบ `Unimplemented`
เงียบ ๆ แล้ว `_poll_swarm` ทุก 1.2 วิ ก็ดึง head กลับเป็น `online[0]` (ลำ 1)

**แก้**:
- `backend/internal/swarm/manager.go` — เพิ่ม `SetLeader()` + `pinnedID` (ตัวที่ผู้ใช้ปักหมุด
  ชนะ auto-pick เสมอถ้ายัง online) และให้ `Start()`/failover เคารพค่านี้
- `backend/internal/api/server.go` — implement gRPC `SetLeader` จริง
- `app.py` — poll ไม่ทับค่าที่ผู้ใช้เลือก ถ้า core ไม่ตรงจะ **ส่ง SetLeader ซ้ำเพื่อแก้ core**
  แทนที่จะยอมตาม (แต่ถ้าลำที่ปักหมุด *หลุด* ยังให้ failover ตามปกติ)

### 11.2 Form up เริ่มก่อนลำแม่ลอยตัว
**อาการ**: กด Take off ในโหมด Swarm แล้ว "ขึ้นทุกลำ ยกเว้นลำแม่" (เป็นบางครั้ง)

**ต้นตอ**: `_await_airborne_then_formup` เดิมเริ่ม Form up เมื่อลอยครบ **n−1 ลำ**
ถ้าลำแม่เป็นตัวที่ arm ช้าที่สุด ขบวนจะเริ่มทั้งที่แม่ยังอยู่บนพื้น → core ใช้ตำแหน่ง/ความสูง
ของแม่ที่ `alt≈0` เป็นจุดอ้างอิง แล้วคำสั่งขบวนไปตีทับ takeoff ของแม่

**แก้**: บังคับรอ**ลำแม่ลอยตัว**ก่อนเสมอ · ถ้าแม่ไม่ขึ้นใน 90 วิ → **ไม่ Form up** +
เตือนแดง · takeoff ของลำแม่ที่ล้มเหลวขึ้น log `⚠ ลำแม่ D1 ขึ้นบินไม่สำเร็จ: <เหตุผลจาก FC>`

### 11.3 Swarm takeoff สั่ง Form up ก่อน takeoff
**ต้นตอ**: ลำดับกลับหัว — `swarm_start()` ถูกสั่งก่อน takeoff 800 ms ทำให้ swarm loop
ยิง `GotoYaw` ใส่โดรนที่ยัง disarm อยู่บนพื้น แล้วตีกับคำสั่ง takeoff ที่ตามมา

**แก้**: `takeoff → รอลอยตัว → ค่อย form up`

### 11.4 Takeoff timeout ไม่พอ + retry loop เป็น dead code
**ต้นตอ**: `service.go` ส่ง context ของ *ทั้งก้อน* (30 วิ) เข้าไปในทุกคำสั่งย่อย
`sendCmd` รอ ACK ด้วย `<-ctx.Done()` → arm ครั้งแรกที่ไม่มี ACK กินงบ 30 วิคนเดียว
loop retry อีก 9 รอบไม่เคยได้ทำงาน แถม client timeout ก็ 30 วิเท่ากันพอดี

**แก้**: แต่ละคำสั่งย่อยมี timeout ของตัวเอง (5 วิ) · งบรวม 30→90 วิ · client 30→120 วิ

### 11.5 GPS ยังไม่ fix แล้วถูกปฏิเสธทิ้งทันที
**ต้นตอ**: สั่ง takeoff พร้อมกันหลายลำ ลำที่ GPS มาช้ากว่าเพื่อน 2–3 วิ ถูก
`CheckArmPrecondition` ปฏิเสธทิ้งทันที ทั้งที่อีกแป๊บเดียวก็พร้อม

**แก้**: เพิ่มแนวคิด `Decision.Transient` แยก "รอแล้วหายได้" (GPS/sat) ออกจาก
"รอไปก็ไม่ดีขึ้น" (แบตต่ำ) · `waitArmReady()` รอ GPS พร้อมสูงสุด 25 วิ
**ความปลอดภัยไม่ลดลง** — ยังไม่ยอม arm ถ้า GPS ไม่พร้อม แค่ให้เวลา

### 11.6 คลิกแผนที่แล้วบินลำเดียว
**ต้นตอ**: `did = self._target_ids()[0]` — เอาแค่ลำแรก (id ต่ำสุด)
**แก้**: สั่งทุกลำที่เลือก + คงรูปขบวน + ส่งตามคิวกันชน

### 11.7 Quick Action ถูก disable ค้าง
**ต้นตอ**: `_select_drone` ปิดปุ่มตอนไม่มี telemetry แต่**ไม่มีใครเปิดคืน**เมื่อมี telemetry แล้ว
**แก้**: เปิดคืนทั้งตอนเลือกลำที่มี telemetry และตอน telemetry ไหลเข้า
(ยังล็อกในโหมด REMOTE ตามเดิม)

### 11.8 ขยายฟอนต์ไม่ครอบคลุม
**ต้นตอ**: widget ตั้ง `font-size` ฝังใน stylesheet ตัวเอง → **ทับ** QSS ระดับแอป
**แก้ 3 ชั้น**: ฟอนต์ฐาน +15% · helper กลางอ่าน scale · `apply_font_scale()` ไล่สเกล
stylesheet ทุก widget (เก็บต้นฉบับไว้ → กดซ้ำไม่บวมสะสม) — สเกลได้ **274 widgets**

### 11.9 Timer ยังทำงานหลังปิดหน้าต่าง (Segfault)
**ต้นตอ**: `closeEvent()` หยุดแค่ telemetry thread แต่ปล่อย QTimer ทั้ง 6 ตัวทำงานต่อ
callback จึงยิงใส่ object ที่กำลังถูกทำลาย
**แก้**: หยุด timer ทุกตัวใน `closeEvent`

### 11.10 Checkbox หลุดเองจาก telemetry สะดุด
**ต้นตอ**: แผง Take off ปลดติ๊กอัตโนมัติเมื่อ telemetry มาไม่ทัน 4 วิ ณ ช็อตที่รีเฟรช
**แก้**: ไม่ปลดติ๊กอัตโนมัติอีก · แยก `update_connectivity()` อัปเดตแค่ป้าย offline
*(ภายหลังแผง checkbox ถูกถอดออกทั้งหมด — ดูข้อ 2)*

### 11.11 E-STOP ไม่เคลียร์สถานะ Waypoint ที่กำลังบิน
**ต้นตอ**: `_do_estop()` เรียก `_abort_rtl()` แต่ไม่แตะ `_waypoint_executing` เลย — กด E-STOP
ระหว่าง waypoint กำลังบิน โดรนหยุดจริงแต่ flag ค้าง `True` ต่อ ทำให้กด Execute เส้นทางใหม่ไม่ได้
(ค้าง toast "กำลังบินอยู่แล้ว") จนกว่าจะกด Cancel Nav แยกต่างหาก
**แก้**: ดึงลอจิกออกมาเป็น `_abort_waypoint_execution()` ใช้ร่วมกันทั้ง `_cancel_navigation()`
และ `_do_estop()` — พบระหว่างตรวจโค้ดเพื่อสรุปแผนที่ความสัมพันธ์ระหว่างฟังก์ชัน (ข้อ 12 มี test คู่)

### 11.12 `help_dialog.py` ลืม import `QWidget`
**ต้นตอ**: เขียนโค้ด footer wrapper ด้วย `QWidget()` แต่ import เฉพาะ `QDialog/QVBoxLayout/...`
— ถ้าไม่มี headless test ที่ construct `HelpDialog` จริง จะไม่รู้จนกว่าผู้ใช้กดปุ่ม "?"
แล้วแอปพัง (`NameError` กลางฟังก์ชัน `__init__`)
**แก้**: เพิ่ม `QWidget` เข้า import · เพิ่ม `test_help_dialog_constructs_and_opens_without_exception`
กันการรีเกรสแบบนี้ในอนาคต

### 11.13 Banner ทำ layout ขยับ + แผนที่วาบขาว
**ต้นตอ**: `self.banner` เดิม `setVisible(False)` ตอนไม่มีข้อความ — Qt ไม่เว้นพื้นที่ให้
widget ที่ซ่อนอยู่ในเลย์เอาต์ พอ banner โผล่/หายกะทันหัน ทั้งแถบใต้ topbar (รวมแผนที่
`QWebEngineView` ด้านล่าง) ขยับ 26px แล้ว resize ทำให้แผนที่วาบขาวชั่วครู่
**แก้**: banner `setVisible(True)` ตลอดเวลา เว้นพื้นที่ 26px ไว้เสมอ · เพิ่ม `_hide_banner()`
เคลียร์แค่ข้อความ+พื้นหลังโปร่งใสแทนการซ่อน widget

### 11.14 `theme._UI_SCALE` (global) ไม่ sync กับ `self._font_scale` (instance) ตอนสร้างแอป
**ต้นตอ**: `self._font_scale` ถูกตั้งใน `__init__` แต่ไม่เคยเรียก `theme.set_ui_scale()`
จนกว่าจะมีการโหลด settings ที่บันทึกไว้หรือผู้ใช้กดเปลี่ยนฟอนต์เอง — widget ที่สร้างตอน
`_build_ui()` เลยใช้ `_UI_SCALE` module-level default (ค่าที่ค้างจาก process/instance ก่อนหน้า
ถ้ามี) แทนที่จะเป็นค่า default ที่ตั้งใจจริง ๆ (พบตอนเพิ่ม test เช็ค default 130%)
**แก้**: เรียก `theme.set_ui_scale(self._font_scale)` ทันทีที่ตั้งค่า `_font_scale` ใน
`__init__` ก่อนสร้าง widget ใด ๆ ทั้งหมด — ค่า default ตอนนี้แน่นอน ไม่ขึ้นกับ state ค้างเก่า

### 11.15 ★ HEAD บนการ์ดเล็ก (FleetItem) บังชื่อโดรน
**ต้นตอ**: `FleetItem` (การ์ดเล็กในลิสต์ FLEET ซ้าย สูงคงที่ 52px) มีทั้งปุ่มดาว
`self.btn_head` (เปลี่ยนสี ☆→★ เหลืองตอนเป็นหัว) **และ** ป้ายข้อความ `lbl_head`
("★ HEAD") วางซ้อนอยู่ในแถวเดียวกับชื่อโดรน (`namerow`) — แถวแคบอยู่แล้ว พอชื่อโดรน
ยาวขึ้นหรือฟอนต์ขยาย (130%) ป้าย "★ HEAD" ก็ไปทับ/บังชื่อโดรน

**หมายเหตุ**: ลองแก้แบบลอยป้ายทับขอบบนของการ์ดก่อน (`SelectedDroneCard` การ์ดล่าง)
แต่นั่นไม่ใช่จุดที่ผู้ใช้หมายถึง — จุดจริงคือการ์ดเล็ก `FleetItem` ด้านบน จึงย้อนกลับ
`SelectedDroneCard` เป็นแบบเดิม (ป้าย ★ HEAD อยู่ในแถวหัวข้อตามปกติ ไม่มีปัญหา)

**แก้**: ตัดป้ายข้อความ `lbl_head` ("★ HEAD") ออกจาก `FleetItem` ทั้งหมด เหลือแค่ปุ่มดาว
`btn_head` สื่อสถานะ Head ด้วย**สีอย่างเดียว** (☆ เทา → ★ เหลือง) ไม่มีข้อความมาแย่งที่
ในแถวชื่ออีกต่อไป

### 11.16 กด Cancel Nav ระหว่างบิน Waypoint แล้ว **โดรนตก**

**อาการ**: กำลังบินตามเส้นทาง Waypoint อยู่ พอกด `CANCEL NAV` โดรนไม่ได้ค้างอยู่กับที่
แต่ร่วงลงพื้นทันที

**ต้นตอ**: `Service.Hold()` ฝั่ง Go สั่ง `SetMode(LOITER)` ตรง ๆ

ใน ArduCopter โหมด `LOITER` / `ALT_HOLD` / `POSHOLD` เป็น **โหมดช่วยนักบิน** —
อัตราไต่/ลง (climb rate) มาจาก **สติ๊กคันเร่งของรีโมท** ไม่ใช่จากตัวคุมอัตโนมัติ
ระหว่างบินอัตโนมัติสติ๊กคันเร่งอยู่ตำแหน่งต่ำสุดเสมอ (และใน SITL ที่รันด้วย
`--no-mavproxy` ไม่มี RC ต่ออยู่เลย ค่าดีฟอลต์ก็คือต่ำสุด) พอสลับโหมดกลางอากาศ
FC จึงอ่านว่า **"นักบินสั่งลง"** แล้วลดระดับด้วยอัตราสูงสุดจนแตะพื้น

เป็นบั๊กที่โผล่ทั้งใน SITL และของจริง — ไม่ใช่ปัญหาเฉพาะโหมดจำลอง

**แก้**: `Hold` เปลี่ยนเป็น "อยู่ `GUIDED` แล้วตรึงพิกัดปัจจุบัน" (รายละเอียดใน §8.2)
`GUIDED` ไม่สนสติ๊กคันเร่ง จึงค้างความสูงเดิมได้จริง และเป็นโหมดเดียวกับที่คำสั่งอื่น
ทั้งหมดใช้ — สั่งบินต่อได้ทันทีไม่ต้องสลับโหมดอีก

ครอบคลุมทุกทางที่เรียก `Hold`: Cancel Nav, ยกเลิก Waypoint, และปุ่ม HOLD ใน Quick Action

**ล็อกกันรีเกรส**: `backend/internal/command/hold_test.go` — ถ้ามีใครเปลี่ยน `holdMode`
กลับไปเป็นโหมดที่กินสติ๊กคันเร่ง เทสต์จะ fail ทันที

### 11.17 ปุ่ม SERVO A/B "กดแล้วไม่ติด" (ไฟสถานะดีเลย์)

**ต้นตอที่ 1 — dead code**: บล็อกที่อัปเดตป้าย/ปุ่มแบบ optimistic ถูกวางผิดที่ —
ไปอยู่**หลัง** `return " · ".join(parts)` ของ `_servo_debug()` แทนที่จะอยู่ท้าย
`_run_servo()` จึงไม่เคยถูกรันเลย ผลคือสถานะปุ่มอ่านจาก telemetry ล้วน ๆ:
กดแล้วต้องรอ core รายงาน `ovr_ch7`/`ovr_ch8` หรือ `RC_CHANNELS` กลับมาก่อนปุ่มถึงจะเปลี่ยนหน้า

**แก้**: ย้ายบล็อกไปที่ `_run_servo()` จริง + เพิ่ม `_servo_pending` (คู่ `(drone_id, label)`
→ `(เจ้าของที่คาดไว้, deadline)`) ที่ `_servo_owner()` เอามาคลุมค่าจริงชั่วคราว
**1 วินาที** — ค่าจริงชนะเสมอเมื่อมาถึงหรือหมดเวลา ปุ่มจึงเด้งกลับเองถ้าสวิตช์รีโมทค้าง
(สั้นกว่า 1.2 วิของ `_verify_servo_released()` เพื่อไม่ให้ปุ่มโชว์ "ปิดแล้ว" พร้อมกับ
banner ที่เตือนว่ายังไม่ปิด)

**ต้นตอที่ 2 — event loop หนักโดยเปล่าประโยชน์**: `_on_telemetry()` เรียก
`pill_link.setStyleSheet(...)` ทุกแพ็กเก็ต (10 Hz × จำนวนลำ = 50 ครั้ง/วิ ที่ 5 ลำ)
ทั้งที่ค่าเหมือนเดิมตลอด — `setStyleSheet` บังคับ Qt re-polish ทั้ง widget
ทำให้คลิกปุ่มแล้วรู้สึกหน่วงโดยรวม

**แก้**: จำสถานะไว้ที่ `_link_pill_state` แล้วทาสีเฉพาะตอนเปลี่ยนจริง
(`_on_stream_error()` รีเซ็ตค่าให้ทาสีเขียวใหม่ตอน link กลับมา)

**ไม่ใช่ SQLite**: ตรวจแล้ว `IpStore` (`~/.swarmgod/fleet_ips.db`) ไม่อยู่บนเส้นทางคำสั่งเลย
`_remember_endpoint()` ที่ถูกเรียกทุกแพ็กเก็ต telemetry มี early-return อยู่แล้วเมื่อ
endpoint ไม่เปลี่ยน (เคยเป็นปัญหาจริง — ดูคอมเมนต์ `PERF:` ใน `app.py`) และฝั่ง Go
`SetRCOverride()` ส่ง `RC_CHANNELS_OVERRIDE` ออกทันทีใน call เดียวกัน ไม่ได้รอ ticker

**หมายเหตุที่ยังคงไว้ตั้งใจ**: ปุ่ม A/B ยังถามยืนยัน 1 ครั้งทุกครั้งที่กด (ทั้งเปิดและปิด)
ตามที่ผู้ใช้กำหนดไว้ เพราะเป็นกลไกปล่อยของจริง

### 11.18 กด A/B **ครั้งแรกหลังเปิดโปรแกรม** ค้างเกือบ 1 วินาที (ครั้งต่อไปเร็วปกติ)

อาการต่อเนื่องจาก §11.17 — หลังแก้ dead code แล้วปุ่มยังรู้สึกหน่วง **เฉพาะครั้งแรก**
ของแต่ละครั้งที่เปิดโปรแกรม

**วิธีหา**: วัดทีละชั้นแทนการเดา (สคริปต์วัดอยู่ใน scratchpad ไม่ได้ commit)

| ชั้นที่วัด | ครั้งแรก (cold) | ครั้งต่อไป (warm) |
|-----------|----------------|------------------|
| `_cmd_servo()` ทั้งเส้น (offscreen, confirm ถูก mock) | 2.5 ms | 2.2 ms |
| `_on_telemetry()` 1 เฟรม | 0.2 ms | 0.2 ms |
| RPC `Servo` ไป core จริง (TCP + mTLS) | 5.8 ms | 0.3 ms |
| **กล่องยืนยัน 1 ใบ (platform=windows)** | **850 ms** | **3 ms** |

**ต้นตอ**: การสร้าง **native window ของ dialog ใบแรก** ใน process — Windows ต้องโหลด
dialog machinery + theme/DWM ครั้งแรก แยกวัดได้ว่า:

| สร้างอะไร | ครั้งแรก |
|-----------|---------|
| `QWidget` ธรรมดา (HWND ใบแรกของ process) | 61 ms |
| `QDialog` | 53 ms |
| `QMessageBox` (ไม่มีไอคอน) | 404 ms |
| `QMessageBox` + ไอคอน | 473 ms |
| `QMessageBox` + ไอคอน + stylesheet ของเรา | ~850 ms |
| stylesheet/CSS ล้วน ๆ | 1.3 ms |

คือ **ไม่ใช่ CSS ของเรา ไม่ใช่ SQLite ไม่ใช่ gRPC ไม่ใช่เซอร์โว** แต่เป็นต้นทุนครั้งเดียว
ของ `QMessageBox` ใบแรก ซึ่งเดิมไปตกที่ "ปุ่มคำสั่งแรกที่ผู้ใช้กด" พอดี

**แก้**: `confirm.prewarm()` — สร้างกล่องยืนยันทิ้ง 1 ใบตอนเปิดโปรแกรม โดยใช้ `winId()`
บังคับสร้าง native window **โดยไม่ map ขึ้นจอ** (ไม่มีหน้าต่างวาบ) เรียกจาก
`_prewarm_ui_paths()` ผ่าน `QTimer.singleShot(250, …)` หลังหน้าต่างหลักโผล่แล้ว
พร้อมอุ่น gRPC channel ใน thread แยกไปด้วย

**ผลวัดหลังแก้**: กดปุ่มครั้งแรก **850 ms → 2.7 ms**
(ต้นทุนก้อน ~470 ms ย้ายไปอยู่ที่วินาทีแรกของการเปิด cockpit แทน — จุดที่ผู้ใช้ยังไม่ได้สั่งอะไร)

ช่วยทุกกล่องยืนยันในแอป ไม่ใช่แค่ A/B (Set Head, DISARM, E-STOP, Clear Waypoint ฯลฯ)

### 11.19 ตัดกล่องยืนยันออกจากปุ่ม A/B — กดแล้วยิงเลย

หลัง §11.18 ฝั่งเทคนิคเหลือ ~3 ms แล้ว แต่ผู้ใช้ยังรู้สึกหน่วง เพราะสิ่งที่เหลือ
**ไม่ใช่โค้ด** แต่เป็น *ขั้นตอน*: กด B → กล่องเด้ง → อ่าน → คลิกยืนยัน = **2 จังหวะ**
ต่อให้กล่องเด้งเร็วแค่ไหนก็ยังเป็น 2 จังหวะอยู่ดี

**การตัดสินใจ**: ผู้ใช้เลือกเอง (เป็นกลไกปล่อยของจริง จึงไม่ตัดสินใจแทน) →
**เอากล่องยืนยันออกจากปุ่ม A/B ทั้งหมด กดแล้วสั่งทันที**

กล่องยืนยันของปุ่มอื่น **ไม่ถูกแตะ** — DISARM, E-STOP (2 ชั้น), Clear Waypoint,
Set Head ยังถามเหมือนเดิม

**สิ่งที่กันพลาดแทน** (ไม่มีอันไหนกินเวลา):

| กลไก | ทำอะไร |
|------|--------|
| ปุ่มเป็น toggle | กดซ้ำ = ยกเลิก + คืนช่องให้รีโมททันที |
| กติกา "1 ห้อง" | รีโมทถือช่องอยู่ → UI สั่งไม่ได้เลย (ปุ่มขึ้น 🔒) |
| `_guard()` | โหมด REMOTE บล็อกทุกคำสั่ง |
| toast + Mission Log | บันทึกทุกครั้งที่กด บอกชัดว่า "เปิด" หรือ "ปิด" กี่ลำ |
| `_verify_servo_released()` | ปิดแล้วเช็คจริงใน 1.2 วิ ถ้าสวิตช์รีโมทค้างจะขึ้น banner แดง |

**เรียงลำดับงานใน `_run_servo()` ใหม่** — ยิง RPC ออกก่อนเป็นอย่างแรก แล้วค่อย
ไฟปุ่ม → toast → log (งานฝั่งจอรอได้อีกไม่กี่ ms แต่ไม่ควรมาคั่นก่อนคำสั่งลงสาย)

**`_on_cmd_result()`**: ผลสำเร็จของ SERVO ไม่ toast ซ้ำแล้ว (log อย่างเดียว) เพราะ
toast ตอนกด ("SERVO B เปิด · 1 ลำ") บอกชัดกว่า "SERVO B D1 สำเร็จ" ที่เดิมมาทับ
ภายในไม่กี่ ms — ผลล้มเหลวยัง toast แดงทับตามปกติ

**ผลวัดหลังแก้** — คลิกปุ่ม → คำสั่งลงสาย + ไฟปุ่มเปลี่ยน:

```
กดปุ่ม B ครั้งที่ 1     3.59 ms   ไฟติด=True  คำสั่งออก=True
กดปุ่ม B ครั้งที่ 2-6   ~2.3 ms   ไฟติด=True  คำสั่งออก=True
```

รวมทั้งสายตั้งแต่ §11.17: **850 ms + 1 คลิก → ~2.4 ms 1 คลิก**

### 11.20 ★ ตัวจริงของ "กดปุ่ม B แล้วหน่วง/ไม่ทำงาน" — ปุ่มถูกบล็อก ไม่ได้ช้า

หลัง §11.17-11.19 ผู้ใช้ยังรายงานว่าปุ่ม B หน่วงอยู่ ทั้งที่วัดฝั่งโค้ดได้ ~2 ms
จึงต่อ **SITL จริง + core จริง** แล้ววัดทั้งสายแทนการเดา — เจอว่ามันไม่ใช่เรื่องความเร็วเลย

**ผลวัดทั้งสาย (SITL จริง)** — สายคำสั่งเร็วอยู่แล้วทุกชั้น:

| ชั้น | เวลา |
|------|------|
| cockpit → core (gRPC unary) | 1.2-1.9 ms |
| core → FC → FC ยืนยันกลับ | 20-100 ms (เพดานคือ telemetry 10 Hz) |

**แต่คำสั่งไม่เคยถูกส่งออกเลย** — diagnostic บน cockpit จริง:

```
rc_ch7_raw = 1000   rc_ch8_raw = 1800      ← ไม่มีรีโมทต่ออยู่เลย
servo_valid= True   sv7=0  sv8=0           ← ขาเซอร์โวยังไม่ขยับ
ovr_ch8    = False
_servo_owner(1,B) = 'RC'                   ← UI คิดว่ารีโมทถือห้อง
ปุ่ม B แสดง: 'B 🔒'
คำสั่งที่ออกจริง: ไม่มีเลย — ถูกบล็อก
toast: 'รีโมทถือ SERVO B อยู่ · ปิดที่รีโมทก่อน'
```

**ต้นตอ**: `_servo_active()` เอา **RC input ดิบ** เป็นตัวตัดสินอันดับแรก
แต่ ArduPilot สตรีม `RC_CHANNELS` มาเสมอ **แม้ไม่มีรีโมทต่ออยู่เลย** โดยเติมค่า
default/failsafe ให้ — วัดกับ SITL จริงได้ **RC8 = 1800** ซึ่งเกินเกณฑ์
`SERVO_ON_MIN = 1500` UI จึงสรุปว่า "มีคนโยกสวิตช์ B ค้างไว้" ตลอดเวลา
แล้วบล็อกการกดทิ้งทั้งหมดตามกติกา "1 ห้อง"

อธิบายอาการที่ผู้ใช้เล่าได้ครบ:
- **ปุ่ม A ใช้ได้ แต่ B ไม่ได้** → RC7 = 1000 (ต่ำกว่าเกณฑ์) แต่ RC8 = 1800 (เกิน)
- **"บางครั้งก็กดได้เลยไม่มีดีเลย์"** → จังหวะที่ยังไม่มี telemetry เข้ามา
  (`_last_telem` ว่าง) โค้ดจะ fallback ไปใช้สถานะที่ UI จำไว้ → ห้องว่าง → กดติด

**แก้**: สลับลำดับความน่าเชื่อถือใน `_servo_active()` — **เอาขาเซอร์โว (servo output)
ขึ้นก่อน RC input**

| ลำดับ | ใช้อะไร | เหตุผล |
|-------|---------|--------|
| 1 | `servo_ch7/8_pwm` | PWM ที่ FC ส่งออกขาเซอร์โวจริง = กลไกขยับจริงหรือยัง |
| 2 | `rc_ch7/8_raw` | สวิตช์รีโมท (ใช้ต่อเมื่อ FC ไม่รายงาน servo output) |
| 3 | สถานะที่ UI จำไว้ | ไม่มีข้อมูลจาก FC เลย |

ขาเซอร์โวไม่โกหกแบบ RC input — ช่องที่ยังไม่ผูกฟังก์ชันรายงาน `0` และเมื่อผูก
`SERVOn_FUNCTION = RCINn` แล้ว ค่าขาออกก็สะท้อนสวิตช์รีโมทให้อยู่ดี
**กติกา "1 ห้อง" จึงยังครบเหมือนเดิม** แต่ตัดสินจากสิ่งที่ขยับจริง
(`_sync_servo_from_telemetry()` ถูกแก้ให้ใช้กติกาเดียวกัน ไม่ให้ป้ายกับปุ่มตัดสินคนละแบบ)

**ผลหลังแก้ (cockpit จริง + SITL จริง)**:

```
ปุ่ม B แสดง: 'B'                     (เดิม 'B 🔒')
คำสั่งที่ออกจริง: [(1, 8, 1950)]      (เดิม: ไม่มีเลย)

คลิกปุ่ม B   GUI ว่างใน 3.6-9.6 ms · ไฟติดทันที · เครื่องบินยืนยันใน 38-98 ms
```

**เพิ่มการวัดถาวรลง Mission Log** — กดทุกครั้งจะได้ 2 บรรทัด
`SERVO B D1: ok (N ms ถึง core)` และ `SERVO B: เครื่องบินยืนยันใน N ms`
คราวหน้าถ้ารู้สึกหน่วงอีก จะเห็นตัวเลขทันทีว่าหน่วงชั้นไหน ไม่ต้องเดา

**PERF เพิ่มเติมที่แก้ไปด้วย** (เจอระหว่างไล่):
- `_refresh_servo_buttons()` เรียก `setStyleSheet` ใหม่ทั้ง 2 ปุ่มทุกแพ็กเก็ต telemetry
  (10 Hz) ทั้งที่หน้าตาเหมือนเดิม = re-parse CSS 20 ครั้ง/วิ บนปุ่มที่ผู้ใช้กำลังจะกด
  → ทาสีเฉพาะตอนสถานะเปลี่ยนจริง (`_servo_btn_mode`)
- `setDroneInfo()` (tooltip บนแผนที่) ยิงเข้า QtWebEngine ทุกแพ็กเก็ต = 50 ครั้ง/วิ ที่ 5 ลำ
  ทั้งที่เห็นเฉพาะตอน hover → ส่งเฉพาะตอนเนื้อหาเปลี่ยน และไม่ถี่กว่า 2 Hz ต่อลำ

### 11.21 "เชื่อมโดรนครั้งแรกแล้วกด B ไม่ติด กว่าจะสั่งได้ พอรอบต่อไปกดปุบปับ"

§11.20 แก้ลำดับให้ดูขาเซอร์โวก่อน RC แล้ว แต่ยังเหลือช่องโหว่: **ถ้ายังไม่มีข้อมูล
ขาเซอร์โวเลย โค้ดจะถอยไปใช้ RC ดิบ** ซึ่งเป็นค่าที่เชื่อไม่ได้

ช่วงเวลาที่เกิดปัญหา = หลังเชื่อมโดรนใหม่ ๆ:

| เวลา | `rc_valid` | `servo_valid` | ผล |
|------|-----------|--------------|-----|
| เพิ่งเชื่อม | ✅ (RC_CHANNELS มาก่อน) | ❌ (SERVO_OUTPUT_RAW ยังไม่มา) | ถอยไปใช้ RC ดิบ = **1800 → ล็อก** |
| สักพัก | ✅ | ✅ | ขาเซอร์โว = 0 → ห้องว่าง → **กดได้ปุบปับ** |

ทั้งสองแฟล็กที่ core มีอายุ 5 วินาที (`time.Since(rcAt) < 5s`) จึง **กะพริบ** ตามจังหวะ
ที่แต่ละสตรีมมาถึง — ช่วงที่ servo หมดอายุแต่ RC ยังไม่หมด ปุ่มก็เด้งกลับไปล็อกเองได้อีก
ทั้งที่ไม่มีอะไรเปลี่ยน และพอ UI ยึดช่องได้ครั้งหนึ่ง `ovr_ch*` = true ก็ตอบ "UI" ทันที
ตลอดไป — ตรงกับที่ผู้ใช้เล่าว่า "รอบถัดไปกดได้เลย"

**แก้**: แยก "ข้อมูลสำหรับแสดงผล" ออกจาก "หลักฐานสำหรับล็อกห้อง"

| ใช้ที่ไหน | ใช้อะไรได้บ้าง |
|-----------|----------------|
| ป้าย A/B บนการ์ด (`_servo_active`) | ขาเซอร์โว → RC → สถานะที่ UI จำ (เหมือนเดิม) |
| **ล็อกห้อง / บล็อกปุ่ม** (`_servo_owner`) | **ขาเซอร์โวเท่านั้น** — ไม่มีข้อมูล = ไม่ล็อก |

เหตุผล: RC input ดิบแยกไม่ออกระหว่าง "มีคนโยกสวิตช์ค้าง" กับ "ไม่มีตัวรับสัญญาณเลย"
(ArduPilot เติมค่า failsafe ให้เสมอ) — **การบล็อกคำสั่งด้วยหลักฐานที่ยืนยันไม่ได้
แย่กว่าปล่อยให้สั่ง** ส่วนกรณีที่ยืนยันได้จริง (ขาเซอร์โวทำงานอยู่โดย UI ไม่ได้ override)
ยังล็อกเหมือนเดิมทุกประการ

**ผลวัด (core ใหม่ + SITL ใหม่ + เชื่อมโดรนสด ๆ)** — ไม่มีรีโมทต่ออยู่เลย `rc8=1800` ตลอด:

```
  หลังเชื่อม   ปุ่ม  owner  servo_valid   rc8   sv8   ผลการกด
       318ms     B   None         None  None  None   ส่งคำสั่ง ✓
       580ms     B   None         True  1800     0   ส่งคำสั่ง ✓
       845ms     B   None         True  1950     0   ส่งคำสั่ง ✓
      1268ms     B   None         True  1800     0   ส่งคำสั่ง ✓
      2262ms ... 8263ms                              ส่งคำสั่ง ✓
```

กฎเดิมจะล็อกทุกแถวในตารางนี้ · ตอนนี้กดได้ตั้งแต่ครั้งแรก

**เทสต์ที่ต้องแก้ตามไปด้วย** — fixture เดิมของ `ServoOwnershipTests` / `ServoToggleTests`
ตั้ง `servo_valid=False` แล้วจำลอง "รีโมทถือห้อง" ด้วย RC ดิบอย่างเดียว ซึ่ง**ไม่ตรงกับ
เครื่องจริง** ที่ตั้ง `SERVOn_FUNCTION = RCINn` ไว้ (ขาเซอร์โวย่อมสะท้อนค่า RC)
ความไม่ตรงตรงนี้เองที่ทำให้บั๊กหลุดรอดมาได้ — แก้ fixture ให้ขาเซอร์โวสะท้อน RC
แล้วทุกเทสต์เดิมยังคุ้มครองกติกา "1 ห้อง" ครบเหมือนเดิม

### 11.22 ★ ปุ่ม B สั่ง PWM ไม่ตรงกับรีโมท (1950 แทนที่จะเป็น 2100)

ผู้ใช้ส่ง Mission Log จากการบินจริงมาให้ ซึ่ง**พิสูจน์ว่าสายคำสั่งเร็วแล้วจริง**:

```
14:43:34  SERVO B CH8 — สั่ง (PWM 1950) · 1 ลำ [RC7=1050 RC8=900 · SV7=0 SV8=900]
14:43:34  SERVO B D1: ok (11 ms ถึง core)
14:43:34  SERVO B: เครื่องบินยืนยันใน 71 ms
```

11 ms ถึง core + 71 ms เครื่องบินยืนยัน — ไม่มีอะไรให้บีบในซอฟต์แวร์อีกแล้ว
และ `RC8=900` ยืนยันว่าบนโดรนจริงของผู้ใช้ ปุ่มไม่เคยถูกล็อกตาม §11.20/§11.21 ด้วย

**แต่ log บรรทัดเดียวกันเปิดโปงบั๊กอีกตัว** — `สั่ง (PWM 1950)` สำหรับ **ช่อง B**

ค่าที่ผู้ใช้วัดจากรีโมทจริง (เขียนเป็นคอมเมนต์อยู่ในโค้ดตั้งแต่แรก):

| ปุ่ม | ช่อง | ปล่อย | กด |
|------|------|-------|-----|
| A | RC7 | 1050 | **1950** |
| B | RC8 | 900 | **2100** |

แต่โค้ดมีค่าคงที่ตัวเดียว `SERVO_ON = 1950` ใช้กับ **ทั้งสองช่อง** — cockpit จึงสั่ง
ช่อง B ที่ 1950 ต่างจากรีโมท 150 µs ถ้าปลายทาง (servo / กลไกปล่อย) ถูก calibrate
ตามระยะของรีโมท ค่านี้จะไป **ไม่สุดระยะ** กลไกขยับช้า/ฝืด/ค้างครึ่งทาง
= อาการ "กดจาก UI แล้วหน่วง แต่กดที่รีโมทติดปุบปับ" ทั้งที่ตัวเลขในซอฟต์แวร์สวยหมด

**แก้**: แยกค่า PWM รายช่องให้ตรงกับรีโมทเป๊ะ

```python
SERVO_PWM_ON  = {"A": 1950, "B": 2100}
SERVO_PWM_OFF = {"A": 1050, "B":  900}
```

กลไกจึงทำงานเหมือนกันไม่ว่าสั่งจาก UI หรือรีโมท ตามที่คอมเมนต์เดิมตั้งใจไว้
("ตรงกับที่รีโมทส่ง") แต่โค้ดทำไม่ได้จริงสำหรับช่อง B

**สังเกตเพิ่มจาก log**: `SV7=0` ตลอด — ช่อง A (SERVO7) ยังไม่ได้ผูกฟังก์ชันไว้ที่ FC
(ยังไม่ตั้ง `SERVO7_FUNCTION = 57`) จึงไม่มีขาเซอร์โวขยับจริง ส่วน `SV8` ทำงานปกติ

### 11.23 เครื่องมือหาว่ากลไกปล่อยของผูกกับช่องไหนจริง (`SWARMGOD_RC_DEBUG`)

หลังแก้ §11.22 log ยืนยันว่าคำสั่งออกครบถ้วนแล้ว:

```
14:57:48  SERVO B CH8 — สั่ง (PWM 2100) · [RC7=1050 RC8=900 · SV7=0 SV8=900]
14:57:48  SERVO B D1: ok (11 ms ถึง core)
14:57:48  SERVO B: เครื่องบินยืนยันใน 102 ms
14:58:18  SERVO B CH8 — ยกเลิก · [RC7=1050 RC8=2100 · SV7=0 SV8=2100]
```

อ่านได้ว่า **FC ส่งออกขาเซอร์โว 8 ที่ 2100 จริง และค้างไว้ 30 วินาที** — ค่าเดียวกับที่
รีโมทส่งเป๊ะ (override ถูกส่งซ้ำทุก 500 ms กัน timeout ~3 วิของ FC) ฝั่งซอฟต์แวร์
**ไม่มีอะไรต่างจากการโยกสวิตช์ที่รีโมทแล้ว**

ถ้ากลไกยังตอบไม่เหมือนกัน แปลว่ามันไม่ได้ผูกกับสิ่งที่ UI สั่ง — แต่ cockpit ติดตาม
แค่ CH7/CH8 จึงมองไม่เห็นว่าจริง ๆ แล้วรีโมทไปขยับอะไร

**เครื่องมือ**: ตั้ง env `SWARMGOD_RC_DEBUG=1` (หรือดับเบิลคลิก **`DIAG_RC.bat`**)
core จะพิมพ์ **RC ทุกช่อง (1-16)** และ **ขาเซอร์โวทุกขา (1-16)** ทุกครั้งที่มีค่าเปลี่ยน
เกิน 20 µs ลง `backend/logs/core-YYYYMMDD.log` บรรทัดขึ้นต้นด้วย `[rcdbg]`

ตัวอย่างจริงจาก SITL:

```
[rcdbg] D1 RC    1=1500 2=1500 3=1000 4=1500 5=1800 6=1000 7=1000 8=1800
[rcdbg] D1 RC    1=1500 2=1500 3=1000 4=1500 5=1800 6=1000 7=1000 8=2100
[rcdbg] D1 SERVO 1=1000 2=1000 3=1000 4=1000
```

เห็นทันทีว่า RC8 ขึ้นถึง 2100 จริง แต่ SITL ตัวนี้ไม่มีขาเซอร์โว 7/8 เลย
(ไม่ได้ตั้ง `SERVOn_FUNCTION`) — ชัดกว่าเดาจากตัวเลขแค่ 2 ช่องมาก

**ขั้นตอนใช้งาน** (หัวใจคือทำ 2 อย่างนี้เทียบกัน):

1. โยกสวิตช์ **B ที่รีโมท** เปิด-ปิด → จดว่าช่อง/ขาไหนขยับ
2. กดปุ่ม **B ที่ cockpit** เปิด-ปิด → จดว่าช่อง/ขาไหนขยับ
3. ถ้าไม่เหมือนกัน = กลไกไม่ได้อยู่บนช่องที่ UI สั่ง (เช่นผูกกับ `RCn_OPTION`
   aux function หรือขาเซอร์โวอื่น) → ต้องแก้ที่พารามิเตอร์ FC ไม่ใช่ที่ cockpit

ปิดโหมดแล้วไม่มีค่าใช้จ่ายใด ๆ — `rcDebugOn` อ่าน env ครั้งเดียวตอน core start
และ `logRC`/`logServo` คืนค่าทันทีถ้าไม่ได้เปิด

นอกจากค่าที่ FC รายงานกลับ ยังพิมพ์ตอน **core ส่ง override ออกไป** ด้วย
(`[rcdbg] D3 SEND override: 8=2100`) เทียบกับบรรทัด `RC`/`SERVO` แล้วรู้ทันทีว่า
ถ้าช้า ช้าที่ฝั่ง core หรือที่เครื่องบิน — พิมพ์เฉพาะตอนชุดช่องเปลี่ยน ไม่ใช่ทุกครั้ง
ที่ resend loop ยิงซ้ำทุก 500 ms

### 11.24 ★★ ต้นตอจริงของ "กดครั้งแรกไม่ติด ต่อไปกดปุบปับ"

จุดสำคัญคือ **โดรนลำนี้คือ `Drone 3`** ไม่ใช่ `Drone 1`

**ต้นตอ — สองบั๊กซ้อนกัน:**

1. `_load_saved_ips()` สร้างการ์ดโดรนจาก IP ที่จำไว้ใน SQLite **ตั้งแต่เปิดโปรแกรม**
   (ลำ offline ก็มีการ์ด) — ตั้งใจให้ผู้ใช้เห็นลำที่เคยต่อ

2. auto-select ใน `_on_telemetry()` อยู่ใน **บล็อก "สร้างการ์ดใหม่" เท่านั้น**:

   ```python
   item = self.fleet_items.get(t.drone_id)
   if item is None:
       ... สร้างการ์ด ...
       if not self._selected_id:
           self._select_drone(t.drone_id)   # ← ไม่ทำงานถ้าการ์ดมีอยู่แล้ว
   ```

   ลำที่เคยต่อมาก่อน **มีการ์ดอยู่แล้ว** จาก SQLite → บล็อกนี้ไม่ทำงาน →
   `_selected_id` ยังเป็น 0 → ไม่มีลำไหนถูกเลือกเลย

3. `_target_ids()` จึงตกไปที่ fallback ซึ่ง **เดาเอาจาก ID ต่ำสุดในฝูง**:

   ```python
   ids = sorted(self.fleet_items.keys())
   return ids[:1] if ids else [1]
   ```

   `fleet_items = {1, 3}` (Drone 1 ค้างจาก SQLite แบบ offline, Drone 3 คือของจริง)
   → ID ต่ำสุด = **1** → คำสั่งวิ่งไปหา **Drone 1 ที่ไม่ได้เชื่อมต่ออยู่**
   → core ตอบ "drone not connected" → เครื่องบินไม่ขยับ

พอผู้ใช้คลิกการ์ด Drone 3 เอง `_selected_ids = {3}` คำสั่งก็ถูกลำทันที = "ต่อไปกดปุบปับ"
และอธิบายได้ด้วยว่าทำไมบางรอบไม่เจอ — ขึ้นอยู่กับว่า SQLite จำ ID ไหนไว้บ้าง
และรอบนั้นโดรนได้ ID อะไร (รอบก่อนหน้าโดรนเป็น `Drone 1` พอดี จึงยิงถูกลำโดยบังเอิญ)

**แก้ 2 จุด:**

| จุด | เดิม | ใหม่ |
|-----|------|------|
| `_on_telemetry()` | auto-select อยู่ในบล็อกสร้างการ์ดใหม่ | ย้ายออกมา — ลำที่ส่ง telemetry มาถูกเลือกให้เสมอถ้ายังไม่มีใครถูกเลือก |
| `_target_ids()` fallback | ID ต่ำสุดในฝูง (รวมลำ offline) | ลำที่ **มี telemetry เข้ามาจริง** (`_connected_ids()`) ก่อนเสมอ |

จุดที่ 2 สำคัญเรื่องความปลอดภัยด้วย — fallback เดิมยิงคำสั่ง (รวมถึง **ปล่อยของ**)
ไปที่ลำที่ผู้ใช้ไม่ได้มอง หรือลำที่ไม่มีอยู่จริง โดยไม่เตือนอะไรเลย

**เทสต์กันรีเกรส 3 ตัว** จำลองเคสนี้ตรง ๆ (SQLite จำ Drone 1, ของจริงคือ Drone 3):
`test_online_drone_is_selected_even_if_card_already_existed`,
`test_command_goes_to_the_online_drone_not_the_lowest_id`,
`test_target_falls_back_to_connected_drone_when_nothing_selected`

### 11.25 เปิดโปรแกรมมาให้ฝูงว่าง — เลิกกู้การ์ด OFFLINE จาก SQLite

ผู้ใช้เลือกเอง: *"ไม่ต้องจำค่าออฟไลน์แล้ว เปิดโปรแกรมมาเดี๋ยวผมกด SCAN หรือ CONNECT เอง"*

`_load_saved_ips()` เดิมสร้างการ์ดโดรนจาก `~/.swarmgod/fleet_ips.db` ให้ทุกลำที่เคย add
(แสดงเป็น OFFLINE) — ตอนนี้ไม่ทำแล้ว ฝูงเริ่มต้นว่างเสมอ

ได้อะไร:
- ตัดความสับสน "ตอนนี้กำลังสั่งลำไหนอยู่" ออกทั้งหมด (ป้องกัน §11.24 ซ้ำในรูปแบบอื่น)
- `_find_duplicate_ip()` ไม่เอา IP เก่าที่ไม่ได้ต่อแล้วมาบล็อกการ connect ใหม่

**ยังทำงานเหมือนเดิม**: SQLite ยังถูกเขียนตามปกติ · ปุ่ม DEL ยังลบออกจากฐานได้ ·
การกัน IP ซ้ำภายในเซสชันยังทำงานครบ — แค่ไม่ถูกอ่านมาสร้างการ์ดตอนเปิดโปรแกรม

อยากได้พฤติกรรมเดิมคืน: กู้โค้ดเวอร์ชันก่อนของเมธอดนี้จาก git history

**ลบ `fleet_ips.db` ทิ้งได้ปลอดภัย** — เก็บแค่ (drone_id, host, port, protocol, name)
ไม่เกี่ยวกับการตั้งค่า cockpit (`cockpit_settings.json`), สีโดรน, แผนที่ offline หรือ log
อย่าสับสนกับ `backend/logs/swarmgod.db` ซึ่งเก็บ users/sessions/vehicle registry/audit index
— **ตัวนั้นห้ามลบ**

### 11.26 ★★★ ต้นเหตุจริงของดีเลย์: MAVLink signing timestamp

บรรทัด `SEND override` (§11.23) ตัดคำถามขาด — core ส่งคำสั่งออกไปตรงเวลาเสมอ
แต่ **FC ทิ้งเฟรมเงียบ ๆ อยู่หลายวินาที** แล้วจู่ ๆ ก็เริ่มรับ จากนั้นเร็วตลอด:

```
17:16:24  SEND override: 8=2100     ← core ส่ง
17:16:48  SERVO ... 8=2100          ← FC เพิ่งขยับ = ทิ้งไป 24 วินาที
                                      (resend loop ยิงซ้ำไปแล้ว ~48 ครั้ง)
```

**ต้นเหตุ**: gomavlib เซ็น MAVLink signature ด้วย timestamp ที่คำนวณจาก
**นาฬิกาของเครื่อง GCS ตรง ๆ** (`pkg/frame/writer.go`):

```go
ff.SignatureTimestamp = uint64(w.timeNow().Sub(signatureReferenceDate)) / 10000
```

ฝั่ง ArduPilot ตอนบูตจะตั้ง signing timestamp ของตัวเองเป็น
**"ค่าที่บันทึกไว้ล่าสุด + 60 วินาที"** เพื่อกัน replay attack (และบันทึกทับทุก 30 วิ)
เฟรมที่ timestamp ต่ำกว่านั้นถูก**ทิ้งทั้งหมดโดยไม่แจ้งอะไรกลับมาเลย**

ผลคือ หลังโดรนบูตใหม่ คำสั่งแรกอาจถูกทิ้งได้นานถึง 1 นาที จนนาฬิกาจริงไล่ทัน
พอไล่ทันแล้ว FC จะจำ timestamp ของเราเป็นค่าสูงสุด — ทุกคำสั่งหลังจากนั้นจึงทันทีตลอด
ตรงกับอาการ "กดครั้งแรกดีเลย์ ต่อไปกดปุบปับ" เป๊ะ

**พิสูจน์แล้วด้วยการวัด** — เครื่องผู้ใช้พบว่า Windows Time service ไม่ได้รัน
(นาฬิกา free-running) พอสั่ง `net start w32time && w32tm /resync /force`:

| | ดีเลย์คำสั่งแรก |
|---|---|
| ก่อนปรับนาฬิกา | **24 วินาที** |
| หลังปรับนาฬิกา | **6 วินาที** |

ที่เหลือ 6 วินาทีคือส่วนที่ ArduPilot ตั้งล่วงหน้าไว้ ซึ่งลดลงเองตามเวลาจริง

**แก้ที่ฝั่งเราไม่ได้**: `timeNow` เป็น field ส่วนตัวของ gomavlib inject offset ไม่ได้
และการ "ปิด signing" ฝั่ง GCS อย่างเดียวจะยิ่งแย่ — ถ้า FC เปิด signing อยู่
มันจะปฏิเสธเฟรมที่ไม่เซ็นสำหรับคำสั่งสำคัญ (รวม RC override) ทันที

**สิ่งที่ทำได้และทำแล้ว — ตรวจจับแล้วบอกผู้ใช้ตรง ๆ**

`Drone.OverrideStuck()` + hook ใน `failsafeTick` (ทุก 1 วิ): ถ้ากำลัง override ช่องหนึ่งอยู่
แต่ค่าที่ FC รายงานกลับยังไม่ตรงกับที่สั่งเกิน 2 วินาที → log + publish event ระดับ WARN
ขึ้นที่ Mission Log ของ cockpit พร้อมสาเหตุที่พบบ่อยที่สุดและวิธีแก้

รายงาน**ครั้งเดียวต่อเหตุการณ์** (รีเซ็ตเมื่อ FC ยอมรับ) ไม่ถล่ม log ทุกวินาที
และไม่สรุปอะไรถ้ายังไม่มีข้อมูล RC มาเทียบ

**วิธีลดดีเลย์ในทางปฏิบัติ**

| วิธี | ผล |
|------|-----|
| ตั้งนาฬิกา GCS ให้ตรง (เปิด w32time + resync) | ลดจาก 24 วิ → 6 วิ (วัดจริง) |
| รอ ~1 นาทีหลังเปิดไฟโดรน ค่อยสั่งคำสั่งแรก | หายสนิท (รอให้พ้นช่วง +60 วิของ FC) |
| ถอด signing key ออกจาก FC | ตัดปัญหาทั้งคลาส (แลกกับความปลอดภัยของลิงก์) |

**เทสต์**: `backend/internal/fleet/override_stuck_test.go` (5 เคส — เงียบตอนปกติ,
เงียบใน grace period, รายงานเมื่อ FC เมิน, ล้างสถานะเมื่อ FC รับ, ไม่เดาเมื่อไม่มีข้อมูล RC)

### 11.27 บั๊กเส้นทาง CONNECT ที่โผล่จาก log เดียวกัน (3 ตัว)

log รอบเดียวกันเปิดโปงบั๊กเพิ่มอีกชุด — คนละเรื่องกับดีเลย์ แต่ร้ายแรงกว่า

**(ก) พอร์ตซ้ำ → เชื่อมต่อไม่ติดเลย**

```
17:52:02  Drone 1 reader started (tcp://192.168.9.146:5760:5760)   ← พอร์ตซ้ำ
17:52:10  Drone 1 reader stopped                                    ← ตายใน 8 วิ
```

ช่อง IP รับได้ทั้ง `192.168.9.146` และ `192.168.9.146:5760` (แอปเองก็เขียนรูปแบบหลัง
ลงช่องนั้นหลัง SCAN — `app.py` บรรทัด `ed_sitl.setText(f"{host}:{port}")`)
แต่ `FleetItem._read_endpoint()` เอาข้อความทั้งก้อนไปเป็น `host` แล้วต่อพอร์ตเข้าไปอีก

**แก้**: `core/ip_scan.split_host_port()` ตัวเดียวใช้ร่วมทุกจุดรับ IP
(การ์ดโดรน · `_card_connect` · `_on_connect_clicked`) รองรับ IPv6 (`[::1]:5760`) ด้วย

**(ข) แถวเก่าใน SQLite บล็อกการ connect ถาวร**

`_find_duplicate_ip()` มีด่านสุดท้ายที่ query SQLite ("กรณี memory ยังไม่ครบ") —
สมเหตุสมผลตอนที่ยังกู้การ์ดจาก SQLite แต่พอฝูงเริ่มต้นว่างแล้ว (§11.25)
แถวใน DB ไม่ได้แปลว่า "โดรนตัวนั้นต่ออยู่ตอนนี้" อีกต่อไป

ผลคือ **IP ที่เคยต่อเมื่อไหร่ก็ตาม จะ connect ไม่ได้อีกเลย** ขึ้น "IP ซ้ำ · ใช้โดย Drone N"
และไม่มีการ์ดให้กด DEL ล้างด้วย — ตันสนิท ต้องไปลบไฟล์ DB เอง

**แก้**: ตัดด่าน SQLite ออก · กติกาที่ถูกคือ "ห้ามต่อโดรน 2 ลำเข้า IP เดียวกัน **ตอนนี้**"
ซึ่งดูจาก endpoint / telemetry / การ์ดในเซสชันปัจจุบันครบอยู่แล้ว

**(ค) `_apply_settings` เป็นเส้นทางกู้การ์ด offline เส้นที่สอง**

§11.25 ปิด `_load_saved_ips()` ไปแล้ว แต่ `cockpit_settings.json` มีคีย์ `saved_ips`
ซึ่ง `_apply_settings()` เอามาสร้างการ์ดใหม่อีกทาง — ฝูงจึงยังไม่ว่างจริง

**แก้**: autoload ตอนเปิดโปรแกรมส่ง `replace_ips=False` เสมอ ·
ปุ่ม **LOAD** ที่ผู้ใช้กดเองยังกู้ IP ได้ตามปกติ (เจตนาชัดเจนกว่า)

### 11.28 บอกด้วยเมื่อ FC กลับมารับคำสั่ง

การเตือนใน §11.26 ทำงานถูกต้องบนโดรนจริง:

```
17:53:58 Drone 1: เครื่องบินยังไม่รับคำสั่ง CH8 (สั่ง 2100 แต่ FC รายงาน 900) มา 2 วินาที …
```

แต่เตือนแล้วเงียบหายไปเลย ผู้ใช้ไม่รู้ว่าตกลงใช้ได้เมื่อไหร่ ต้องกดใหม่ไหม
เพิ่ม `OverrideRecovered()` → ขึ้น event ระดับ OK ครั้งเดียวตอน FC เริ่มรับ:
`เครื่องบินรับคำสั่งแล้ว (ใช้เวลา N วินาที)`

### 11.29 ตารางค่า PWM ของรีโมท และจุดที่ค่าเหล่านี้มีผลกับระบบ

ค่าที่ผู้ใช้ตั้งไว้ที่รีโมทจริง (ยืนยันแล้ว):

| ปุ่ม | ช่อง | ปล่อย | กด |
|------|------|-------|-----|
| A | RC7 | 1050 | 1950 |
| B | RC8 | **900** | **2100** |

ค่าพวกนี้ไหลไปเกี่ยวกับ **4 จุด** ในระบบ — ตรวจครบแล้วทุกจุด:

| จุด | ค่าที่ใช้ | สถานะ |
|-----|----------|--------|
| PWM ที่ cockpit ส่งตอนกด (`SERVO_PWM_ON`) | A=1950 · B=2100 | ✅ ตรงรีโมทเป๊ะ (แก้ที่ §11.22) |
| เส้นแบ่ง "เปิด/ปิด" (`SERVO_ON_MIN`) | 1500 | ✅ อยู่กลางระหว่างปล่อยกับกดของทั้งสองช่อง |
| ช่วงที่ core ยอมรับ (`ClampServoPWM`) | 900–2100 | ✅ ครอบพอดี **2100 ไม่ถูกตัด** |
| ค่าตอนปล่อย (`SERVO_PWM_OFF`) | A=1050 · B=900 | ℹ️ อ้างอิงเท่านั้น ไม่ได้ส่งออก |

จุดที่ 3 สำคัญ — ถ้า `ServoPWMMax` เป็น 2000 ตามค่านิยมทั่วไป ช่อง B จะถูก core ตัดจาก
2100 → 2000 เงียบ ๆ แล้วกลไกไปไม่สุดระยะเท่ารีโมท · ของโปรเจคนี้ตั้งไว้ 2100 พอดีอยู่แล้ว

**จุดที่ 4 ไม่ได้ถูกส่งออกไปไหน** — การปิดจาก UI ใช้วิธี *ปล่อย override คืนช่องให้รีโมท*
(`servo_release`) ค่าที่ช่องตกลงไปจึงเป็นค่าจริงจากสวิตช์ ไม่ใช่ค่าที่เราสั่ง
เก็บไว้เป็นค่าอ้างอิงสำหรับตรวจสอบเท่านั้น (เดิมไม่มีคอมเมนต์กำกับ อ่านแล้วเข้าใจผิดได้)

**เทสต์ที่คุ้มครองไว้** — จะ fail ทันทีถ้าไปตั้งสวิตช์รีโมทใหม่แล้วค่าหลุดกรอบ:
- `test_threshold_separates_released_from_pressed_on_every_channel` —
  ค่าปล่อยต้อง < 1500 < ค่ากด ของทุกช่อง (ถ้าหลุด ระบบจะอ่านสถานะกลับด้าน:
  ปุ่มขึ้น 🔒 ทั้งที่ไม่มีใครกด หรือคิดว่าปิดทั้งที่เปิดอยู่)
- `test_pwm_stays_inside_the_range_core_accepts` — ค่าต้องอยู่ใน 900–2100 ไม่โดน clamp

**ยังพิสูจน์ไม่ได้ 100% ว่าเป็น signing** — สมมติฐานนี้อธิบายอาการได้ครบและสอดคล้องกับ
ผลตอน sync นาฬิกา (24→6 วิ) แต่ยังไม่ได้ตัดตัวแปรออกโดยตรง

**วิธีพิสูจน์ให้จบใน 1 นาที** — `TEST_NOSIGNING.bat`
(ตั้ง `SWARMGOD_MAVLINK_SIGNING=off` แล้วเปิด launcher ให้)

| ผลที่เจอ | แปลว่า |
|---------|--------|
| กดแล้วทำงานทันที ไม่มีดีเลย์ | ✅ signing timestamp คือต้นเหตุ · FC ไม่ได้บังคับ signing → ปิดถาวรได้ |
| กดแล้วไม่ทำงานเลย | FC **บังคับ** signing อยู่ ต้องเปิดไว้ · ดีเลย์มาจากเรื่องอื่น |

⚠️ โหมดนี้ลิงก์ MAVLink จะไม่มีลายเซ็น ใช้เฉพาะตอนทดสอบ

**เรื่องรีโมท (G12 / MX330)** — จาก log ฝั่งรีโมท**ไม่มีอะไรต้องแก้**:
- `RC 8` เปลี่ยน 900 ↔ 2100 ตรงตามที่ตั้งไว้
- `SERVO 8` เดินตาม `RC 8` ทุกครั้ง = `SERVO8_FUNCTION` ตั้งถูกแล้ว
- ปล่อย override เมื่อไหร่ ค่ากลับไป 900 ทันที = รีโมทคุมช่องคืนได้ปกติ

ดีเลย์เกิด**หลังจาก**คำสั่งออกจาก core ไปแล้ว จึงไม่เกี่ยวกับการตั้งค่าที่รีโมทหรือแอป
(`SERVO7_FUNCTION` ยังไม่ได้ตั้ง — ปุ่ม A จึงยังไม่มีขาเซอร์โวขยับจริง ถ้าจะใช้ต้องตั้งเพิ่ม)

### 11.31 ★ ผลทดสอบปิด signing — **สมมติฐานเดิมผิด**

รัน `TEST_NOSIGNING.bat` บนโดรนจริง (20:45):

20:45:41  Drone 1 reader started · SERVO 8=900 · RC 8=900
20:45:51  SEND override: 8=2100
20:45:54  WARN: ยังไม่รับ มา 3 วินาที
20:45:58  SERVO 8=2100                    ← ช้า 7 วินาที
20:45:59  SEND (ปล่อย) → SERVO 8=900  วินาทีเดียวกัน  ✓
20:46:01  SEND 8=2100  → SERVO 8=2100 วินาทีเดียวกัน  ✓
20:46:04 / 20:46:08 …                     ✓ ทันทีทุกครั้ง

อ่านได้ 2 อย่างพร้อมกัน:

| ผล | สรุป |
|----|------|
| ปิด signing แล้ว **ยังสั่งได้** | FC **ไม่ได้บังคับ** signing |
| ปิด signing แล้ว **ดีเลย์ยังอยู่ 7 วิ** | **signing ไม่ใช่ต้นเหตุ — §11.26 ผิด** |

**บันทึกไว้ว่าสมมติฐานเดิมผิด** เพื่อไม่ให้ใครไปไล่ทางเดิมซ้ำ · §11.26 ยังมีประโยชน์
ตรงกลไกตรวจจับ แต่คำอธิบายสาเหตุในนั้นถูกหักล้างแล้วด้วยการทดลองนี้

**สิ่งที่ตัดออกไปแล้วทั้งหมด (วัดจริงทุกข้อ)**

| ตัวแปร | วิธีตัดออก | ผล |
|--------|-----------|-----|
| ฝั่ง cockpit | วัด click → RPC | ~2 ms |
| ฝั่ง gRPC | วัด RPC → core | ~11 ms |
| ค่า PWM | เทียบกับที่รีโมทส่ง | ตรงเป๊ะรายช่อง (§11.22) |
| ช่อง/พารามิเตอร์ FC | `DIAG_RC.bat` | SERVO8 เดินตาม RC8 ทุกครั้ง |
| การ์ด offline / เลือกผิดลำ | §11.24-11.25 | แก้แล้ว |
| นาฬิกา GCS | sync w32time | ลดลงจริง (24→6/7/11) แต่ **ไม่หาย** |
| **MAVLink signing** | `SWARMGOD_MAVLINK_SIGNING=off` | **ดีเลย์ยังอยู่** |

เหลือข้อเดียว: **FC เมิน `RC_CHANNELS_OVERRIDE` ชุดแรกหลังเชื่อมต่อ**
เวลาจากเชื่อมต่อถึงคำสั่งแรกสำเร็จค่อนข้างคงที่ — **17, 17, 15, 17 วินาที**
(รอบ 39 วิเป็นรอบเดียวที่นาฬิกายังไม่ sync)

### 11.32 บรรเทาด้วย RC warm-up ตั้งแต่เชื่อมต่อ

ยังไม่รู้ว่า gate อยู่ตรงไหนใน ArduPilot แต่รูปแบบชัดว่าเป็น *"ข้อความชนิดนี้ชุดแรก
จากเราถูกเมิน"* — ถ้าให้ FC ได้เห็น stream นี้ก่อนผู้ใช้กดจริง ก็น่าจะผ่านช่วงนั้นไปแล้ว

`Drone.RCWarmup()` — เริ่มทันทีที่เชื่อมต่อ (`Manager.Connect` spawn ให้)
ส่ง `RC_CHANNELS_OVERRIDE` แบบ **"ปล่อยทุกช่อง"** (ทุก field = 0) ทุก 500 ms เป็นเวลา 25 วิ

ทำไมปลอดภัย:
- ค่า `0` ในสเปก MAVLink = **"คืนช่องให้ RC จริง"** → ไม่แตะการควบคุมใด ๆ เลย
- หยุดทันทีเมื่อมีคำสั่งจริงเกิดขึ้น (ปล่อยให้ `rcOverrideLoop` รับช่วง)
- หยุดเมื่อ connection ปิด หรือส่งไม่สำเร็จ
- จำกัด 25 วินาที — ไม่กลายเป็นการยิง override ตลอดอายุการบิน

> เป็นการ **บรรเทาแบบตั้งสมมติฐาน** ไม่ใช่การแก้ที่ต้นเหตุที่พิสูจน์แล้ว

**ผลทดสอบบนโดรนจริง (21:02)** — ดีเลย์คำสั่งแรก **7 วิ → 3 วิ**:

```
21:02:54  Drone 1 reader started
21:02:55  SEND override: (ไม่เหลือช่องไหน override อยู่)   ← warm-up เริ่มทันที
21:03:03  SEND override: 8=2100      ← ผู้ใช้กด (9 วิหลังเชื่อมต่อ)
21:03:06  SERVO 8=2100               ← FC รับ = 3 วินาที
21:03:09  SEND → SERVO วินาทีเดียวกัน   ✓
21:03:21  SEND → SERVO 1 วิ (ระหว่างบิน)  ✓
```

รอบนี้ **ไม่มี WARN** เลย — FC รับก่อนตัวตรวจจับ (เกณฑ์ 2 วิ) จะทัน

**สรุปพัฒนาการทั้งหมด**

| รอบ | เงื่อนไข | ดีเลย์คำสั่งแรก |
|-----|---------|----------------|
| 17:16 | นาฬิกา GCS ไม่ sync | 24 วิ |
| 17:37 | sync นาฬิกาแล้ว | 6 วิ |
| 19:31 | sync | 11 วิ |
| 20:45 | + ปิด signing | 7 วิ |
| **21:02** | **+ RC warm-up** | **3 วิ** |

⚠️ **ยังสรุปไม่ได้ 100%** — n=1 และรอบก่อน ๆ แกว่ง 6-11-7 วิอยู่แล้ว
3 วิต่ำกว่าทุกรอบก็จริง แต่ต้องวัดซ้ำอีก 2-3 รอบถึงจะแยกออกจากความแกว่งปกติได้

ถ้ายืนยันแล้วยังเหลือ ~3 วิ ขั้นถัดไปคืออ่านพารามิเตอร์จาก FC จริง:
`SYSID_MYGCS` (ArduPilot รับ override เฉพาะ sysid ที่ตรง — เราส่งด้วย 255) ·
`RC_OPTIONS` (bit 1 = Ignore MAVLink Overrides) · `RC8_OPTION` (aux function ทับช่อง)

### 11.33 ยืนยันผล warm-up (n=5) + ปรับเกณฑ์เตือนตามความจริงใหม่

ทดสอบซ้ำ 5 รอบ **โดยเปิด signing กลับตามปกติแล้ว**:

| รอบ | เชื่อมต่อ | WARN | ดีเลย์ |
|-----|----------|------|--------|
| 21:10 | 21:10:33 | ไม่มี | < 2 วิ |
| 21:11 | 21:11:26 | 2 วิ | ~2 วิ |
| 21:12 | 21:12:29 | ไม่มี | < 2 วิ |
| 21:13 | 21:13:23 | 3 วิ | ~3 วิ |
| 21:13:50 | 21:14:08 | 2 วิ | ~2 วิ |

**ก่อน warm-up: 6, 7, 11, 24 วิ → หลัง: <2, 2, <2, 3, 2 วิ** — ยืนยันว่าไม่ใช่ความบังเอิญ
และได้ผลเท่ากันทั้งตอนเปิดและปิด signing (ตอกย้ำ §11.31 ว่า signing ไม่เกี่ยว)

**ปัญหาใหม่ที่ log ชุดนี้เผย — แก้แล้วทั้งคู่:**

**(ก) คำเตือนกลายเป็น noise** · เกณฑ์ `overrideStuckAfter` ตั้งไว้ 2 วิ ตอนที่ดีเลย์ปกติ
คือ 6-24 วิ พอ warm-up ทำให้เหลือ 2-3 วิ คำเตือนเลยเด้ง**แทบทุกเที่ยวบิน**
ซึ่งฝึกให้คนมองข้ามคำเตือน → ขยับเป็น **5 วิ** ให้เตือนเฉพาะตอนผิดปกติจริง
(เทสต์ผูกกับค่าคงที่จริงแล้ว ไม่ใช่ตัวเลขดิบ — ปรับเกณฑ์อีกก็ไม่พัง)

**(ข) เตือนแล้วไม่มีตอนจบ** · ทั้ง 5 รอบมีแต่ WARN ไม่มี "เครื่องบินรับคำสั่งแล้ว" เลย
สาเหตุ: `OverrideRecovered()` คืน false ทันทีถ้า override ถูกยกเลิกไปแล้ว —
ผู้ใช้กดปิดก่อน FC จะรับ เลยไม่มีใครรายงาน ตามผลไม่ได้ว่าตกลง FC รับหรือผู้ใช้ยอมแพ้

เพิ่ม **`OverrideLatency()`** — วัดเวลาที่ FC รับ "คำสั่งแรกของการเชื่อมต่อ"
รายงานครั้งเดียวต่อการเชื่อมต่อ **แม้จะเร็วกว่าเกณฑ์เตือน**:

```
[fleet] Drone 1: FC รับคำสั่งแรกหลังเชื่อมต่อใน 2.3 วินาที
```

ทำให้มีตัวเลขเทียบผลได้ทุกเที่ยวบินโดยไม่ต้องเปิด `SWARMGOD_RC_DEBUG`
— ก่อนหน้านี้พอปรับจนเร็วกว่าเกณฑ์แล้ว log จะเงียบสนิท วัดผลต่อไม่ได้เลย

### 11.34 ★★★ เจอของจริง: `SYSID_MYGCS` ไม่ตรงกับ sysid ที่ core ส่ง

ผู้ใช้อ่านค่าจาก FC มาให้:

| พารามิเตอร์ | ค่าที่ตั้งไว้ | ควรเป็น |
|-------------|-------------|---------|
| `SYSID_MYGCS` | **250** | ต้องตรงกับ sysid ที่ GCS ส่ง |
| `RC_OPTIONS` | 0 | ✅ ไม่ได้บล็อก override |
| `RC8_OPTION` | 0 | ✅ ไม่มี aux function ทับช่อง |

**แต่ core hardcode ส่งด้วย sysid `255` มาตลอด** (`mavlink.Dial(..., 255, ...)`)

ArduPilot รับ `RC_CHANNELS_OVERRIDE` **เฉพาะจาก GCS ที่ sysid ตรงกับ `SYSID_MYGCS`**:

```cpp
void GCS_MAVLINK::handle_rc_channels_override(const mavlink_message_t &msg)
{
    if (msg.sysid != sysid_my_gcs()) {
        return;   // ทิ้งเงียบ ๆ ไม่มี error ตอบกลับ
    }
```

รีโมท G12 + แอป MX330 ตั้ง `SYSID_MYGCS = 250` ไว้ (เป็น sysid ของตัวควบคุมเอง)
ส่วน 255 เป็นค่ามาตรฐานของ GCS ทั่วไป (Mission Planner ฯลฯ) — **ไม่ตรงกัน**

**แก้**: ทำให้ตั้งได้ผ่าน config/env แทนการ hardcode

```
SWARMGOD_MAVLINK_SYSID=250
```

- `config.MAVLinkSysID` ค่าเริ่มต้น 255 (ไม่เปลี่ยนพฤติกรรมเดิมของ setup อื่น)
- รับค่า 1-255 เท่านั้น ค่านอกช่วง/ไม่ใช่ตัวเลข → คงค่าเริ่มต้น
- **พิมพ์ค่าที่ใช้ตอน core boot เสมอ** เทียบกับค่าใน FC ได้ทันทีเวลาสั่งแล้วไม่ทำงาน:

```
[fleet] MAVLink System ID (GCS) = 250 — ต้องตรงกับ SYSID_MYGCS ที่ FC
```

- `START_SYSID250.bat` — preset สำหรับเครื่องนี้ กดทีเดียวจบ

**หมายเหตุเรื่องเวลาที่วัดได้** — log ชุด 21:26-21:29 (ก่อนแก้ sysid) แกว่งมาก:
**5.0 · 1.1 · 5.9 · 13.9 วินาที** ซึ่ง sysid ที่ไม่ตรงกันแบบตายตัวน่าจะทำให้
คำสั่งถูกทิ้ง **ตลอดไป** ไม่ใช่แค่ช้า — แปลว่ายังมีกลไกอื่นร่วมด้วย (อาจเป็นการที่
ArduPilot บางเวอร์ชันไม่ได้บังคับเช็ค หรือรีโมทเขียนค่าอะไรบางอย่างเป็นระยะ)

จึงยัง **ไม่ฟันธงว่านี่คือคำตอบสุดท้าย** — แต่เป็น misconfiguration จริงที่ต้องแก้
ไม่ว่าจะช่วยเรื่องดีเลย์หรือไม่ · วัดผลหลังตั้ง 250 แล้วจะรู้

### 11.35 ผล sysid 250 + เปลี่ยนแนวทาง: ให้ปุ่มบอกสถานะแทนการเดา

**ตั้ง `SWARMGOD_MAVLINK_SYSID=250` ให้ตรงกับ FC แล้ว — ไม่ได้ช่วย**

| sysid ที่ core ส่ง | เวลาที่ FC รับคำสั่งแรก |
|-------------------|------------------------|
| 255 (ไม่ตรงกับ FC) | 5.0 · 1.1 · 5.9 · 13.9 วิ |
| **250 (ตรงกับ FC)** | **24.7 · 11.7 วิ** |

ไม่ดีขึ้น (n น้อยและแกว่งสูงมาก จึงสรุปไม่ได้ว่าแย่ลงจริง) — **สมมติฐาน sysid ผิดอีกข้อ**
คงค่า 250 ไว้เพราะตรงกับที่ FC ตั้งไว้ตามหลักการ แต่ไม่ได้แก้ดีเลย์

**สมมติฐานที่ลองแล้วผิดทั้งหมด**: MAVLink signing · นาฬิกา GCS · ค่า PWM ·
`SYSID_MYGCS` · `RC_OPTIONS` / `RC8_OPTION` (ทั้งคู่ = 0 อยู่แล้ว)
**ได้ผลจริงข้อเดียว**: RC warm-up (§11.32) ลดจาก 6-24 → 2-3 วิ แต่ยังแกว่ง 1-25 วิ

#### เปลี่ยนแนวทาง — คำถามผู้ใช้ชี้ทางออกที่ถูกกว่า

> *"ผมอยากรู้ว่าพอเลือกลำโดรนแล้วต้องรออีกกี่วิถึงจะกดปุ่ม B ได้
> เพราะผมไม่รู้เลยว่ากดตัวโดรนแล้วผมกด B เลย"*

ปัญหาที่แท้จริงไม่ใช่ "ช้ากี่วินาที" แต่คือ **ผู้ใช้ไม่มีทางรู้ว่าเกิดอะไรขึ้น**
คำสั่งไม่เคยหาย — core ส่งซ้ำทุก 500 ms จน FC รับ — แต่ระหว่างนั้นปุ่มดูเหมือน
"ไม่ได้สั่ง" เลยกดซ้ำ ๆ (ซึ่ง**ยกเลิก**คำสั่งที่กำลังรออยู่!) หรือรอเก้อ

**แก้: เพิ่มสถานะที่ 4 บนปุ่ม — `⋯` รอเครื่องบิน**

| ปุ่ม | ความหมาย | ที่มาของข้อมูล |
|------|----------|----------------|
| `A` | ห้องว่าง | ไม่มี override, ขาเซอร์โวปิด |
| `A ⋯` | **สั่งแล้ว กำลังรอเครื่องบิน** | core override อยู่ **แต่ขาเซอร์โวยังไม่ขยับ** |
| `A ●` | **ยืนยันแล้ว** | core override อยู่ **และขาเซอร์โวขยับจริง** |
| `A 🔒` | รีโมทถือห้อง | ไม่มี override แต่ขาเซอร์โวเปิด |

ใช้ข้อมูลจริงจาก FC ล้วน ไม่มีการเดา · ถ้าไม่มี `servo_valid` จะไม่แสดง `⋯`
(สรุปไม่ได้ = ไม่เดา) · tooltip บอกชัดว่า **"ไม่ต้องกดซ้ำ · กดซ้ำ = ยกเลิก"**

ผู้ใช้จึงไม่ต้องรู้ว่า "ต้องรอกี่วิ" อีกต่อไป — ดูที่ปุ่มได้เลย

Help modal อัปเดตแล้วทั้งตารางสถานะปุ่มและกล่องเตือนอธิบายพฤติกรรม 1-25 วินาที

### 11.36 หน้ารหัสผ่านก่อนเข้าโปรแกรม

`widgets/login_dialog.py` + `core/auth.py` — ถามรหัสก่อนเข้า launcher

**ถามที่เดียว**: launcher ถาม → cockpit ที่ launcher เปิดต่อได้ธง `SWARMGOD_AUTHED=1`
จึงไม่ถามซ้ำ · แต่ถ้าเปิด cockpit ตรง ๆ (`python -m swarmgod_gui`) จะถามเหมือนกัน
ไม่มีทางลัดเข้าโดยไม่ผ่านรหัส

**เก็บรหัสเป็น SHA-256 ไม่ใช่ตัวเปล่า** — เปิดไฟล์ดูแล้วไม่เห็นรหัสตรง ๆ
(มีเทสต์ยืนยันว่าไม่มีรหัสเป็น plaintext ในซอร์ส)

เปลี่ยนรหัสได้โดยไม่ต้องแก้โค้ด เรียงตามลำดับ:
1. env `SWARMGOD_PASSCODE=<รหัสใหม่>`
2. ไฟล์ `~/.swarmgod/passcode` (บรรทัดเดียว)

> ⚠️ **ขอบเขต**: เป็นประตูกันคนกดเล่น **ไม่ใช่ระบบความปลอดภัยจริง** — โปรแกรมรันบน
> เครื่องผู้ใช้เอง ใครเข้าถึงไฟล์ได้ก็แก้/ข้ามได้ · สิ่งที่กันการสั่งโดรนจริงคือ
> mTLS + token ที่ core (ดู docs/SECURITY.md)

**ดีไซน์**: เข้าชุดกับ cockpit (graphite dark) — โลโก้หน่วย · การ์ดยกระดับ + เงานุ่ม ·
ช่องรหัสแบบ masked ตรงกลาง · กด Enter ได้เลย
รหัสผิด = กรอบแดง + **สั่นการ์ด** + ข้อความบอก · พิมพ์ใหม่ = ล้างสถานะแดงทันที
แถวข้อความ error **เว้นที่ไว้เสมอ** ไม่ทำ layout ขยับตอนโผล่/หาย (บทเรียนจาก §11.13)

**บทเรียนตอนทำ — การพิมพ์ภาษาไทย**

| ปัญหา | แก้ |
|-------|-----|
| `letter-spacing` กับข้อความไทย | สระบน/ล่างและวรรณยุกต์เป็น combining mark — letter-spacing ดันให้หลุดจากพยัญชนะ **ตัดออกจากข้อความไทยทั้งหมด** เหลือไว้เฉพาะ "SWARMGOD" ที่เป็นละตินล้วน |
| ใช้ `FONT_MONO` กับข้อความไทย | ฟอนต์ mono ไม่มี glyph ไทยที่ดี → เปลี่ยนเป็น `FONT_FAMILY` (Segoe UI) |

**ข้อควรระวังตอนตรวจ UI**: `QT_QPA_PLATFORM=offscreen` บนเครื่องนี้ **วาดข้อความไม่ได้เลย**
(QLabel เปล่า ๆ ก็หาย) — เกือบทำให้วินิจฉัยผิดว่าเป็นบั๊กของ drop shadow
ตรวจ UI ที่มีข้อความต้อง render ด้วย platform จริง (`QT_QPA_PLATFORM=` ว่าง)
แล้วใช้ `grab()` โดยไม่ `show()` — ได้ภาพจริงโดยไม่มีหน้าต่างเด้งขึ้นจอ

**เทสต์** `frontend/tests/test_login.py` (14 เคส) — รหัสถูก/ผิด · เว้นวรรค ·
ไม่มี plaintext ในซอร์ส · env/ไฟล์ override · ช่องเป็น masked · error ไม่ทำ layout ขยับ ·
พิมพ์ใหม่ล้าง error · ธง `SWARMGOD_AUTHED` ข้ามการถามซ้ำ · เปิดตรง ๆ ยังถาม

### 11.37 ★ อุ่นเครื่องช่อง A/B ให้เองอัตโนมัติ + บอกสถานะ "พร้อม"

เดิมทางแก้คือบอกผู้ใช้ว่า *"กด A/B ทิ้ง 1 ครั้งตอนอยู่บนพื้นก่อน"* ซึ่งไม่สะดวกและลืมง่าย
ผู้ใช้เสนอให้โปรแกรมทำเองในเบื้องหลังแล้วขึ้นสถานะบนปุ่ม — ทำตามนั้น

**กลไก** (`_prime_servo` / `_check_servo_primed` ใน `app.py`)

1. โดรนเข้าฝูงและมี `rc_valid` → ส่ง `servo_set(ch, SERVO_PWM_PRIME)` เงียบ ๆ
2. เฝ้า telemetry จน RC ของช่องนั้น echo ค่ากลับมา = **FC ตอบรับแล้ว**
3. `servo_release(ch)` คืนช่องให้รีโมท → ทำเครื่องหมายว่าช่องนี้ **พร้อม**
4. ไม่ตอบใน 20 วิ → เลิกรอ ปล่อย override ปลดล็อกปุ่มให้ใช้ตามปกติ (ไม่ค้าง ⌛ ตลอดกาล)

**ความปลอดภัย — จุดที่ต้องระวังที่สุดของฟีเจอร์นี้**

| กฎ | เหตุผล |
|----|--------|
| ค่าอุ่นเครื่องอยู่ใน **ย่านปิด** (1200) ไม่ใช่ค่าเปิด (1950/2100) | ถ้าใช้ค่าเปิด **กลไกจะปล่อยของทันทีที่เปิดโปรแกรม** |
| ต่างจากค่าปล่อยเกิน 20 µs | ต่ำกว่านี้แยกไม่ออกจาก noise → ตรวจไม่ได้ว่า FC ตอบรับ |
| อยู่ในช่วง 900-2100 | นอกช่วงนี้ core clamp ทิ้ง |
| ข้ามช่องที่ `_servo_owner` ไม่ว่าง | เคารพกติกา "1 ห้อง" — ไม่แย่งช่องจากรีโมท |
| ปล่อย override ทันทีที่เสร็จ | ไม่ค้างถือช่องไว้ |
| ล้างสถานะเมื่อลบโดรนออกจากฝูง | ต่อกลับมาใหม่ FC เริ่มนับใหม่ ต้องอุ่นอีกรอบ |

เซอร์โวจะขยับเล็กน้อยในย่านปิดแล้วกลับที่เดิม (B: 900→1200→900)
**ต้องทดสอบบนพื้นโดยไม่ใส่ของก่อนใช้งานจริงทุกครั้งที่เปลี่ยนกลไก**

**สถานะบนปุ่ม — ครบ 5 สถานะแล้ว**

| ปุ่ม | ความหมาย |
|------|----------|
| `A ⌛` | โปรแกรมกำลังเตรียมช่องให้เอง (กดได้ แต่คำสั่งแรกอาจหน่วง) |
| `A` | **พร้อมใช้งาน** — กดแล้วติดทันที |
| `A ⋯` | สั่งแล้ว รอเครื่องบินตอบรับ (ไม่ต้องกดซ้ำ) |
| `A ●` | เครื่องบินยืนยันแล้ว (ขาเซอร์โวขยับจริง) |
| `A 🔒` | รีโมทถือห้องอยู่ |

Mission Log บันทึกให้ด้วย: `SERVO B พร้อมใช้งาน (เตรียมเสร็จใน N วินาที)`

**เทสต์** `frontend/tests/test_servo_prime.py` (11 เคส) — ค่าอุ่นเครื่องอยู่ในย่านปิด ·

## 13. PRE-FLIGHT SUMMARY V2 — แผนและลำดับทำงาน

ส่งผลต่อ operation และส่วน **EXECUTION FLOW** แสดง state ที่ยืนยันจาก command,
RPC, telemetry, `target_reached` และเงื่อนไข WAVE จริง

- จุด `ACTIVE` กระพริบเป็นเพียงสัญญาณภาพ; timer ไม่มีสิทธิ์เปลี่ยน business state
- TAKEOFF รอ telemetry ยืนยัน airborne และถึง target altitude; SWARM จะไม่ FORM UP
  ก่อน Head พร้อมจริง
- Waypoint แสดง WP ปัจจุบันและ A/B เมื่อถึงจุดจริง; WAVE จะไม่เริ่มกลุ่มใหม่จนกลุ่มก่อน
  disarm ครบ
- Cancel Nav, WAVE cancel และ E-STOP ทำให้ run ปัจจุบัน `CANCELLED` และขั้นที่เหลือ
  `SKIPPED`; callback ที่มี run id เก่าจะถูกละทิ้ง

## 14. ข้อควรรู้

1. **แก้ฝั่ง Go ต้อง rebuild + restart core** ไม่งั้นโค้ดใหม่ไม่ถูกใช้:
   ```bash
   cd backend && go build -o bin/swarmgod-core.exe ./cmd/swarmgod-core
   ```
   (เคยเจอกรณีแก้แล้วอาการเดิม เพราะ core ที่รันอยู่ยังเป็น binary เก่า)

2. **ค่าที่บันทึกไว้จะถูกโหลดทับค่าดีฟอลต์** — `~/.swarmgod/cockpit_settings.json`
   ถ้าเคยเซฟ `rtl_alt` ไว้ค่าอื่น เปิดมาจะเห็นค่านั้น ไม่ใช่ 2 m
   (ความหมายของช่องนี้เปลี่ยนจาก "ความสูงชั้นล่างสุด" → "ค่าที่บวกเพิ่ม" — ถ้าเคยเซฟไว้
   แนะนำตั้งใหม่แล้วกด SAVE)

3. **RTL ใช้จุด home ที่จำจากตอนโดรนอยู่บนพื้น** (`alt_rel < 1.5 m`)
   ถ้าไม่มีข้อมูล จะ fallback ไปใช้คำสั่ง RTL ของ FC แทน
